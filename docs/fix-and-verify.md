# Bug Proof и Fix & Verify для загруженных Python-проектов

Обновление AI Engine: workflow расширен на существующие JS/TS implementation-модули; syntax/build проверяются внутри Playwright gVisor image. Для `analyze` и `propose-fix` теперь обязательно серверное согласие с hash проекта и провайдера. Единый адаптер, примеры body, бюджеты и ограничения описаны в [ai-engine.md](ai-engine.md). Численные pytest-лимиты ниже относятся к Python-профилю.

## Рабочий путь

1. Выполнить сохранённый pytest-план в Test Studio. Assertion failure или нарушение `pytest.raises` связывается с требованием и точным тестом; статус — **Reproduced**. Неожиданные неподтверждённые причины остаются Suspected.
2. В Bug Lab прочитать требование, код теста и traceback. Пользователь явно подтверждает корректность ожидания и пишет обоснование. API связывает review с run UUID, SHA256 теста и состоянием проекта.
3. Сервер повторяет **точный исходный снимок** в новом gVisor-контейнере с тем же image ID. Набор и результаты кейсов должны совпасть, целевое assertion-падение — повториться. Ошибки окружения, пропуски и неоднозначные case IDs запрещают Confirmed. После успеха — **Confirmed** с явно записанным основанием: review пользователя + повторный прогон.
4. «Предложить патч» отправляет контекст выбранному OpenAI-compatible провайдеру после отдельного UI-уведомления. Операция асинхронная, возвращает job ID. LLM возвращает структурированные замены файлов; сервер сам строит unified diff.
5. «Проверить в копии» выполняет три независимых одноразовых runsc-контейнера:
   - полный исходный снимок, чтобы снова подтвердить baseline;
   - исправленные исходники + неизменённый модуль целевого теста;
   - исправленные исходники + весь неизменённый сохранённый pytest-план.
6. Сравниваются case IDs `(test UUID, classname, case name)`, результаты, ошибки/пропуски и все ранее проходившие кейсы. Все кейсы полного набора должны пройти; список нельзя сократить. Только после этого — **Fix Verified**.
7. «Подтвердить применение» показывает отдельный диалог. API требует `confirm=true`, конкретные fix UUID / verification UUID / SHA256 показанного патча. Исходники, документы, требования, Gherkin и тесты должны по-прежнему совпадать с проверенным состоянием.
8. Применение создаёт новые blob-файлы и атомарно переключает ссылки на них в DB. Предыдущие версии сохраняются. Исправленный проект можно скачать ZIP-архивом; внешняя рабочая папка пользователя автоматически не редактируется.

## Ограничения изменения

- Только существующие `.py` файлы из исходного снимка; до трёх файлов, суммарно до 200 изменённых строк.
- Запрещены новые файлы, traversal, дубликаты, тестовые пути и launcher/pytest/coverage infrastructure.
- Перед каждой заменой сверяется SHA256 исходника; новый Python проходит AST parse без исполнения на API-хосте.
- LLM не передаёт исполняемые patch/shell команды. Его raw diff не применяется: diff вычислен сервером из before/after.
- Генерировать заново, переписывать, удалять или менять ожидания тестов во время проверки нельзя. В gVisor передаются сохранённые строки исходного pytest-кода.
- Источник и тесты не меняются ни при предложении, ни при проверке. Правки через API во время проверки инвалидируют результат по общему хэшу состояния.
- Ошибка повторной проверки отзывает verified; старый успешный attempt не позволяет обойти новый отказ.

## Что означает результат

UI отдельно показывает «исходная проблема исправлена», «не обнаружены регрессии», число ранее проходивших контрольных кейсов и «полная корректность приложения не доказана». При отсутствии отдельных контрольных кейсов это явно указано. Регрессионный набор — все сохранённые pytest-модули Test Studio, а не автоматическое обнаружение любых тестов в произвольном репозитории.

Confirmed здесь включает **ручное подтверждение соответствия assertion требованию**. Это не автоматическое формальное доказательство и не независимый математический oracle. Недоверенный Python-процесс может пытаться исказить свой отчёт; прежняя модель доверия gVisor остаётся в силе. Нельзя считать ответ LLM достаточным подтверждением.

Каждая проверка сохраняет baseline/focused/regression, runtime, image ID, fingerprint снимка, кейсы, traceback, coverage и assessment. UI позволяет выбрать версию diff и раскрыть предыдущие попытки. Failed verification сохраняет уже полученные измерения и причину отказа.

## REST

| Endpoint | Действие |
|---|---|
| POST `/api/bugs/{id}/confirm-proof` | 202; `confirm_expectation`, `reviewer_note`, `run_id`, `test_sha256` |
| POST `/api/bugs/{id}/propose-fix` | 202 для загрузок, job ID; доверенное demo сохраняет старый синхронный контракт |
| POST `/api/bugs/{id}/verify-fix` | 202; `{ "fix_id": "UUID" }` |
| POST `/api/bugs/{id}/apply-fix` | `{ "confirm": true, "fix_id": "UUID", "verification_id": "UUID", "patch_sha256": "SHA256" }` |
| GET `/api/projects/{id}/fixes` | Версии предложений, diff, hashes, application backup metadata |
| GET `/api/projects/{id}/runs` | История proof/propose/verify, полные измерения |
| GET `/api/projects/{id}/source-archive` | Текущие сохранённые исходники и документы ZIP |

Ошибки: 409 — устаревшее/неподтверждённое состояние или неверное подтверждение, 422 — невалидная схема, 503 — нет AI / gVisor / очереди. При смене разрешённого sandbox image повтор старого снимка закрывается с понятной ошибкой: сначала нужен новый run на текущем образе.

## Защита применения

Мутации проекта сериализуются PostgreSQL row lock на Project. Copy-on-write не меняет старые blob-файлы. Все новые файлы записываются и fsync выполняется до DB commit; ссылки нескольких файлов переключаются одним commit. При ошибке второго файла транзакция откатывается целиком. Если подтверждение DB commit потеряно, новые blobs удаляются только когда свежая DB-сессия доказала отсутствие ссылок на них. Иначе они сохраняются, чтобы не удалить уже применённые данные. Повтор подтверждённого apply идемпотентен.

## Проверка

```sh
docker compose -f docker-compose.yml -f compose.test.yml up --build -d
python tests/compose/fix_verify_smoke.py
```

Провайдер только в этом override — явно тестовый, origin `llm-contract-test`; планы/патчи подготовлены, gVisor-прогоны настоящие. Проверяются успех, отдельное подтверждение, отсутствие изменений до apply, неизменность тестов, отклонение регрессии, история двух предложений и отказ после изменения проекта.

Browser E2E `tests/e2e/uploaded-run.spec.ts` проходит весь UI, включая отказ от диалога применения, последующее согласие, скачивание ZIP и повторный зелёный прогон. Unit/integration проверяют политики diff, несколько файлов, сбой записи, потерянный commit acknowledgement и изменение ожиданий после verify.
