# Автономный AI QA — фактическая проверка

> Исторический отчёт предыдущей серии. Последующий Python live-прогон успешно завершён; актуальное состояние и ограничения: [mvp-readiness.md](mvp-readiness.md). Неудачные попытки ниже сохранены без изменения результатов.

20 октября 2026, Asia/Tomsk. FastAPI / React / Celery / PostgreSQL / Docker Compose / gVisor. Модель пользователя: `gpt-6-luna`, провайдер: `https://triklz27.ru/v1`.

**Главный критерий достигнут частично: полностью автономный live workflow подтверждён для нового JS/TS-проекта, но НЕ подтверждён для нового Python-проекта. Общая автономность двух языков не заявляется.** JS/TS прошёл от загрузки до проверенного AI-патча без ручного решения по результатам. Оба неуспешных Python-запуска сохранены, ни один из них не был принят или исправлен агентом вручную. Live-патчи не применялись.

## Причины прежних ложных отказов

Предыдущий reviewer возвращал `approved` и свободный текст. Не было обязательной связи каждого вывода с конкретными assertions и цитатами документа; техническая исполнимость не проверялась до рецензии. Reviewer мог превращать пожелания о покрытии в требования, неверно прослеживать изменение состояния, требовать определённую последовательность примеров и отклонять CSS-селектор из-за отсутствия DOM-описания в бизнес-документе. Отказ непосредственно запускал регенерацию или останавливал анализ. Ручное принятие черновика доказывало работоспособность набора, но не автономность.

Старые прогоны не переименованы в автономные. Исходные проекты и ранее выполненные тесты не изменены ради успешной проверки.

## Новый многоуровневый путь

Доступен через кнопку **«Автономный QA»** для нового загруженного проекта или `POST /api/projects/{id}/autonomous`. Перед стартом требуется согласие на передачу очищенных данных выбранному провайдеру и весь обозначенный QA-цикл. Применение патча в это согласие не входит.

1. **Структура.** Pydantic, запрет лишних полей, ограничения размеров, неизменяемые серверные требования и проверяемые ссылки. После ошибок Python-протокола генерация автономного режима переведена на schema `scenarios` без повторного вывода списка требований. Ключ требования и framework ограничены enum, а сервер присоединяет ранее извлечённые требования. Это не сопоставление ошибочных ссылок «по догадке».
2. **Синтаксис.** Python AST, JS/TS esbuild; исходники и тесты проверяются также внутри отдельного gVisor-контейнера. Загруженный код не импортируется и не исполняется на API/worker/host.
3. **Обнаружение тестов.** Фиксированные `pytest --collect-only` или `Playwright --list` внутри runsc. Проверяются непустое обнаружение всех модулей, уникальные identities и привязка результата к SHA снимка и образу. Падающий product assertion не является ошибкой discovery. Исполнение позже должно вернуть тот же состав кейсов.
4. **Смысл.** Отдельный структурированный запрос получает исходные требования, Gherkin, код тестов и явно пронумерованные assertions, без реализации приложения, результатов его выполнения и oracle. Для каждого сценария обязательны verdict, точная цитата и полный список индексов assertions. Поддержка ожидаемых значений — суждение LLM, а не формальная математическая гарантия.
5. **Неподтверждённые ожидания.** Неописанное или неоднозначное поведение должно получить `ambiguous`. Одного синтаксического успеха, прохождения collection или желания получить зелёный прогон недостаточно для принятия теста.
6. **Расхождение.** Разрешена отдельная перепроверка. Для отмены отказа обязательны независимые контраргументы к каждому спорному сценарию: точная цитата прежнего утверждения, фрагмент теста, цитата документа и обоснование. Без них отказ не снимается. Это отдельный запрос той же выбранной модели, не независимый производитель или человек.
7. **Ограниченная коррекция.** Максимум одна коррекция нового набора до исполнения. Исходные требования сохраняются. Результаты продуктовых тестов и приватных oracle в регенерацию не поступают. После первого исполнения тесты не меняются.
8. **Безопасность.** Статический preflight отклоняет известные опасные конструкции, пропуски и тривиальные проверки. Реальной границей остаётся gVisor: фиксированные образы и команды, non-root, read-only rootfs, network=none, no capabilities, cgroups, дедлайны, отсутствие ключей и Docker socket в госте. Статические проверки не объявляются доказательством безвредности произвольного кода.

| Ситуация | Классификация / действие |
|---|---|
| Не проходит AST/esbuild | `syntax_error`; одна ограниченная коррекция до исполнения |
| Пустой набор, дубли, ошибки collection, skip/tautology | `invalid_test`; исправление или остановка |
| Assertion противоречит документу | `requirement_contradiction`; независимая проверка, затем ограниченная коррекция либо остановка |
| Ожидание не следует из документа / спор не разрешён | `manual_review_required`, `requirement_ambiguity`; исполнения и подтверждения дефекта нет |
| Отказ опровергнут привязанными к источникам аргументами | `reviewer_false_rejection`; принятие возможно только после технических проверок |
| Не найден/неоднозначен UI locator | `manual_review_required`, `test_binding_ambiguity`; автоматическое доказательство дефекта запрещено |
| Сбой runner, окружения, transport или response schema | отдельная инфраструктурная/протокольная ошибка; не дефект приложения |
| Проверенное ожидание + assertion failure + точный replay | Bug Proof с `review_kind=automated_validation`, без утверждения о ручном одобрении пользователем |

`manual_review_required` — терминальный статус, не успешная валидация. Сохраняются черновики, технические наблюдения и валидированные структурные ответы рецензента в записи проекта; общие AI-логи не содержат исходников/ответов/замечаний или ключей. Для ошибок evidence добавлены фиксированные диагностические коды, без копирования чувствительного текста в журнал.

## Автономный workflow

В одном явном задании: extraction → Test Plan / Gherkin / code → layered validation → gVisor execution → классификация → Bug Proof → настоящий LLM diff → baseline / focused / full regression → QA-отчёт. Сохраняются отдельные записи фаз и происхождение тестов `llm-autonomous-validated`.

Автоматический Bug Proof допускается только при связанной серверной валидации того же проекта, состояния, плана и SHA теста; replay должен повторить весь набор статусов в том же образе. Подтверждение не приписывается человеку. Патч проверяется существующим механизмом Fix & Verify. Ни orchestration, ни benchmark не вызывают apply.

Для всего задания используется один AIAdapter с общими существующими calls/tokens/USD/deadline; переключение стадии не обнуляет бюджет. Предельные выходные токены фаз могут быть только ниже пользовательской настройки: extraction 1800, генерация/коррекция 3000, semantic review 1200, adjudication 1400, patch 1800. Согласие и lineage состояния сохраняются. Исходники и уже выполненные тесты защищены прежними блокировками и SHA.

Новый путь обязателен для **«Автономный QA»**. Прежний отдельный `AI-анализ` и ручной Bug Lab сохранены как совместимый самостоятельный workflow; результаты их старой рецензии не являются новой автономной сертификацией.

- `team_invoice_v2`: React/TypeScript, планы, годовая скидка, фиксированный сбор и сохранение состояния при отсутствии согласия с условиями.

Эти задания ранее не участвовали в демонстрациях. Oracle, seed locations и reference changes находятся отдельно в `evaluation/oracle_tests` и `evaluation/variants.json`. Они не включались в generation/review/patch context. Evaluator использует их отдельно; его данные не возвращаются модели. Повтор Python использовал новый экземпляр тех же публичных входов, без обратной связи скрытых испытаний.

У первой Python-попытки старый общий код `invalid_structure` не сохранял достаточного payload, чтобы достоверно определить, какой именно evidence-check нарушился: coverage, цитата или индексы. В дальнейшем добавлены точные категории, сохранение проектных semantic responses, явные индексы и проверка по полному исходному документу, а не только excerpt извлечения. Новая успешная live-проверка Python после этого не проводилась из-за общего ограничения серии. Нельзя утверждать, что последняя правка уже устранила Python live-проблему.

- **11 настоящих LLM POST**: 7 структурно принятых ответов, 4 протокольных/evidence ошибки. Все ответы с model сообщают `gpt-6-luna`. Это идентификатор стороннего шлюза; независимая аттестация его inference отсутствует.
- Usage доступен у всех 11 ответов: **18084 prompt + 10515 completion = 28599 токенов**. Суммарное время LLM-попыток — **122.665 s**.
- Консервативный reservation — **$1.90001**, **не фактический счёт**. Денежную стоимость провайдер не сообщил.
- Модель, ключ, endpoint и пользовательские верхние лимиты не увеличивались. При повторе общий дневной live-cap временно **снижен** до 12 запросов / $2, охватывая все попытки этой серии; затем восстановлены прежние значения 50 / $20. Лимит одного задания остался $1. Остатка серии недостаточно для ещё одного полного цикла, новые live-запросы не выполнялись.

Контрактный provider в регрессионных тестах возвращает подготовленные ответы, не считается настоящей генерацией и не добавлен к live-метрикам.

## Ограничения и следующий шаг

1. Полный критерий «новый Python + новый JS/TS автономно» **НЕ достигнут**. Для Python нужна ещё одна отдельно разрешённая ограниченная live-серия на финальной версии протокола.
2. Смысловая валидация LLM остаётся вероятностной. Точные ссылки и независимый запрос уменьшают произвольные решения, но не доказывают логическое следование всех ожиданий документу.
3. Gherkin проверяется по структуре заголовков и смысловой рецензии, не полным Cucumber parser. JS/TS syntax проверяется esbuild; полный TypeScript typecheck не выполняется.
4. Runtime locator ambiguity останавливает автоматическое доказательство, но универсально отличить любой ошибочный тест от любого дефекта невозможно; неоднозначность должна оставаться ручной, не успешной.
5. Контроли небольшие; две задачи не дают оценки качества на произвольных проектах. Coverage и число тестов не используются как общий балл качества.
6. Полные исходники передаются только с согласием, после privacy-фильтра; фильтрация секретов эвристическая. Проектные черновики и отчёты требуют той же защиты доступа, что и загруженный код.

