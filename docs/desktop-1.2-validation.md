# Debugych Desktop 1.2: проверка Windows-релиза

Дата: 27.10.2026. Ветка `release/debugych-desktop-1.2`, отдельный worktree. Основа - актуальная 1.1, commit `0bfd841`, включая последние изменения QA-экранов, а не устаревший `f08536d`. Main и параллельная 3D-ветка не менялись.

## Результат и границы готовности

Собран устанавливаемый Windows-клиент x64 с одним Debugych.exe, главным окном и встроенным Desktop Pet v3.2.1. Установка, обновление, удаление, ярлыки и запуск установленного бинарника проверены на текущей настоящей Windows. Это пригодная для дальнейшей приёмки сборка, но полная Windows release acceptance пока не завершена: чистая VM и повтор всех интерактивных действий двух окон остаются NOT TESTED. Сертификата подписи нет. SmartScreen, TLS и ограничения gVisor не отключались.

## Изменения

- Штатный Tauri CLI 2.12.4 / NSIS 3.13, currentUser. Resources установлены рядом с EXE, включены Node с лицензией, production frontend, embedded pet и существующий backend bootstrap. Системные Node/Python/npm не нужны для запуска самого клиента.
- Ярлык в «Пуск», опциональный ярлык рабочего стола, регистрация удаления, запуск приложения с завершающего экрана. Пользовательские данные не входят в установщик.
- Новый стабильный identifier `local.debugych.desktop.client` устраняет передачу запуска старой portable 1.0/1.1. Поиск старой версии сверяет полный путь процесса и release manifest, показывает PID/путь и предлагает закрыть её. Процессы по имени не завершаются.
- Отдельно сохранён каталог `%APPDATA%/local.debugych.desktop`: новый identifier не должен создавать пустой пользовательский профиль. При тестировании обнаружено, что первоначальная реализация этого переноса не попала в код; исправлено. Финальная установленная сборка использует прежний профиль и сохранила выбранный реальный проект.
- Стандартная принудительная остановка приложения в NSIS заменена проверкой точного установленного файла через Restart Manager. Работающая версия должна быть закрыта пользователем. Silent update тоже отказывается продолжать. Старые portable-ярлыки не удаляются.
- Добавлены системный трей и команды открытия окна, показа/скрытия питомца, диагностики, подключения и полного выхода.
- Экран диагностики показывает конфигурацию, доступность API, runner/gVisor, Playwright, настройку live AI и Linux Docker/runsc. Диагностика не отправляет completion-запрос и не выдаёт наличие ключа за подтверждение доступности провайдера или баланса.
- Local/Remote используют прежний общий Runtime, backend adapter и bridge. В Remote нет запуска WSL/Docker/backend. Нужен HTTPS origin, без credentials в URL. Будущая авторизация описана отдельно, фактического серверного деплоя нет.

AI Engine, backend API, Runner, Bug Proof/Fix & Verify, спрайты, риг и анимации не менялись. Согласие на LLM и подтверждение применения патча остаются прежними.

Новые browser-тесты используют явно контрактный native adapter, а не настоящий Windows IPC или LLM. Новые Rust-проверки отличают реальный доступный sandbox от одной только конфигурации, не считают AI configuration живой проверкой, распознают старую версию по manifest и проверяют завершение настоящего принадлежащего приложению дочернего процесса. Process smoke запускал установленный EXE с отдельными QA-профилями, ограниченным PATH и рабочим каталогом TEMP. Это не имитация чистой VM. Remote не породил node/wsl/docker/powershell для backend; Local породил только принадлежащие клиенту Node и WSL keepalive. Завершение smoke-клиентов выполнено по точным созданным Process objects, не по имени, с проверкой ухода дочерних процессов. Это принудительная очистка тестовых экземпляров, а не доказательство штатного tray exit.

Подтверждены сохранение connection.json, выбранного проекта и отсутствие удаления существующего профиля. Отдельная миграция настроек localStorage/WebView2 между identifiers не проверена. Через установленный loopback proxy прочитаны 2 требования, 4 тест-кейса, 9 сохранённых запусков и 1 исправление контрольного проекта: Bug Proof существует, status=fix_verified, verified=true, applied=false. Новые задания не создавались.

Первая проверка cleanup смотрела слишком рано, через 300 мс: WebView renderer завершился чуть позже. Исправлен тестовый harness: ждёт завершения до 5 секунд. Первая проверка uninstall тоже наблюдала промежуточное состояние, пока temp uninstaller ещё удалял shortcut/registry; повторная проверка дождалась всех трёх условий. Эти первоначальные наблюдения сохранены, не скрыты.

## Ограничение инструмента Windows UI

В первой части проверки использован computer-use skill: настоящие окна, GUI NSIS, диагностика, конфликт версий и восстановление. Затем helper перестал отвечать на `get_window_state` и даже `list_windows` (`computer-use request timed out`). После повторного запроса и reset JS-сессии ошибка сохранилась. Дальнейшие UI-вводы остановлены согласно recovery workflow. Поэтому интерактивные проверки трея и двух окон не объявляются успешными на основании тестов 1.1. Один установочный тестовый процесс был принудительно очищен по известному PID/пути; это явно отмечено в evidence.

Непрерывную запись native WebView2 средствами GDI получить не удалось: аппаратная композиция дала пустые тёмные кадры. Пустые ролики исключены из поставки. Вместо них подготовлен `debugych_desktop_1.2_overview.mp4`: 12-секундный обзор трёх реальных контрольных кадров, с постоянной подписью «Не непрерывная запись экрана». Он не доказывает интерактивный lifecycle.

## Зависимости и безопасность

Windows x64, WebView2, включённый Node runtime. Для local QA отдельно нужны Linux Docker, зарегистрированный runsc/gVisor и образы pytest/Playwright. В Remote эти зависимости находятся на будущем сервере. Отсутствие ключа не препятствует запуску клиента и просмотру результатов. Подробная памятка - `server-migration-readiness.md`.

Платные LLM-запросы не выполнялись. Для регрессии использованы сохранённые реальные результаты, без новой генерации и без применения патча. Локальные listener проверяются на loopback; общие контейнеры и volumes не останавливались. Серверные ключи и локальные `.env`/история чата не включаются в архивы. Backend migration/auth остаются отдельным обязательным этапом перед публикацией API в интернет.

## Воспроизведение

1. `npm ci` в apps/web, apps/pet и apps/desktop; Rust/MSVC SDK и Python нужны только для сборки.
2. `scripts/build-windows-app.ps1` создаёт EXE, portable ZIP, NSIS installer и source ZIP.
3. `scripts/test-desktop-pet-browser.ps1` и `scripts/test-desktop12-browser.ps1` используют отдельные временные контейнеры с отключённой сетью, не перезапускают рабочий стек.
4. `scripts/test-installed-desktop12.ps1` проверяет установленный клиент с отдельными QA-профилями. Скрипт явно отличает process smoke от native UI и чистой VM.
5. Сырые результаты и контрольные кадры находятся в `outputs/desktop12`; устанавливаемый EXE также копируется в `outputs/Debugych-Desktop-1.2.0-Setup.exe`.

Перед публичным релизом: закончить native acceptance на исправном UI helper, повторить установку/обновление/удаление в чистой Windows VM, записать непрерывное видео двух окон и получить подпись издателя. Main не объединялся.
