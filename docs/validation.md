## Настоящие результаты доверенного Python demo

- До исправления: **13 passed / 1 failed**. Упавший тест `test_exact_balance` проверяет R1: `pay(1000, 1000)` должен вернуть True, возвращает False.
- После `>` → `>=`: **14 passed / 0 failed**. Выполнены исходный тест и все контрольные проверки регрессии.
- Повторный запуск после отдельного применения также проходит. До применения сохранённый исходник не меняется; проверка выполняется во временной копии.
- Измеренное coverage.py покрытие: **86,67% совокупно по строкам и ветвям**; 20/24 исполняемых строк, 6/6 ветвей. Четыре непокрытые строки относятся к HTTP-обработчику FastAPI. Это не 100% покрытие и не доказательство полной корректности.
- JUnit cases, stdout, traceback и полный coverage JSON сохраняются в run records; API / Reports показывают фактические данные.

Backend integration использует реальный `execute()` runner, заменяя только HTTP transport. Playwright workflow проверяет отдельно запущенный runner через HTTP: результаты не подменяются.

## Браузерные доказательства

Подготовленный магазин доступен на `/api/demo-web`; `?fixed=true` включает исправленную доверенную версию JS-логики. Playwright вводит баланс и сумму, нажимает кнопку и проверяет результат. Buggy-версия намеренно нарушает assertion. `test.fail` включается **после** успешной навигации, ввода и записи доказательства, поэтому ранняя инфраструктурная ошибка не засчитывается как найденный дефект. Отчёт содержит `bug-proof.json`, `exact-balance.png`, шаги и trace ожидаемого assertion-падения.

HTML-отчёт: `apps/web/playwright-report/index.html`. Trace и screenshot: `apps/web/test-results`. Этот браузерный набор пока запускается CLI/CI; в Bug Lab API он не интегрирован. Универсальное исполнение загруженного Playwright отсутствует.

## Исправленные при проверке проблемы

- Очистка временной SQLite в Windows: закрытие основного pool и NullPool в Alembic.
- Смешение create_all и миграций: локальный startup теперь применяет Alembic; существующая собственная development DB была приведена к версии 001, затем обновлена до 002.
- Неоднозначный Playwright selector Test Studio: точное accessible name.
- Риск отображения ответа старого проекта при переключении: проверка текущего selection перед применением ответа.
- Неопределённый порядок histories в PostgreSQL: timestamp records, миграция 002 и явная сортировка.
- Гонка между завершённым job и списком результатов при параллельном чтении: UI теперь сначала читает статус, затем результаты, чтобы не останавливаться с пустыми данными после завершения.
- Невалидный Python в LLM response: синтаксическая проверка без исполнения, повтор в пределах бюджета.

## Непроверенное и незавершённое

- Docker CLI отсутствует: контейнеры не собирались, `docker compose up` не выполнялся. PostgreSQL, Redis/Celery и фактическая эффективность container limits требуют Linux/Docker smoke. CI-конфигурация создана, но удалённый CI не запускался.
- Нет LLM API key: live-генерация и совместимость выбранного провайдера не проверены. Провайдерский contract unit test — не доказательство живого AI.
- Не выполнено нагрузочное тестирование PDF 50+ страниц. Извлечение вынесено в worker, ответ API содержит job ID.
- Нет изоляции для произвольного недоверенного кода: выполнение пользовательских проектов запрещено, prepared demo явно обозначено.
- Generic LLM patch/verify, Java execution, Istanbul, pgvector, полноценная отмена задач, отдельные ORM таблицы всех сущностей и многопользовательская авторизация не реализованы.
- Один upstream DeprecationWarning Starlette TestClient / AnyIO; тесты не падают.

Следующий приоритет: проверить Compose на Linux с PostgreSQL/Celery, затем создать и проверить внешнюю sandbox, прежде чем включать исполнение загруженных проектов. Это требуется для завершения полного конкурсного MVP; текущий результат — рабочая основа и доказанный доверенный сквозной сценарий.
