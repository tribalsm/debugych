# AI Engine: настройка, согласие, бюджеты и проверка

## Настройка настоящего провайдера

Скопируйте `.env.example` в `.env` в корне проекта и заполните:

```dotenv
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=your-provider-api-key
LLM_MODEL=your-supported-model
```

Нужен API-ключ выбранного провайдера. Учётные данные release/ChatGPT автоматически не используются. `.env` исключён из Git и исходного архива. Ключ передаётся только доверенным API/worker; gVisor-контейнеры его не получают. Наличие ключа означает «настроен», а не «проверен живой моделью».

После настройки выполните из корня `docker compose up -d --force-recreate api worker` (в PowerShell доступен `scripts/compose.ps1`). Статус: `GET /api/ai/status`; приложение — `http://127.0.0.1:8080/`. Endpoint не показывает ключ. Без ключа AI-анализ/новое предложение недоступны с явной ошибкой; ранее сохранённые тесты и проверка патча продолжают работать. Подготовленный провайдер включается только отдельным `compose.test.yml` и явно маркируется.

По умолчанию используется Chat Completions-compatible `/chat/completions`, `response_format=json_schema`, strict JSON Schema и `max_completion_tokens`. Модель должна поддерживать этот контракт. Для старого совместимого провайдера явно задайте `LLM_RESPONSE_FORMAT=json_object`: схема тогда включается в инструкцию и всё равно проверяется Pydantic на backend. Автоматического переключения после ошибки 400 нет. Если провайдер не понимает `max_completion_tokens`, нужен совместимый endpoint; такой провайдер пока не поддерживается без изменения адаптера.

## Один транспорт и два этапа анализа

`services/ai/adapter.py` обслуживает все live/contract запросы. `engine.py` сначала извлекает требования **только из документов**, требует source path и точную quote. Backend проверяет наличие цитаты в соответствующем очищенном документе. Второй запрос получает исходники, обзор AST/структуры и эти требования, создаёт Gherkin и исполняемый план. Ключи, порядок и текст требований не могут самовольно меняться; framework должен соответствовать профилю. Python AST проверяется без исполнения. TS/JS реально проверяются при сборке/collection в gVisor.

Наличие точной цитаты доказывает происхождение фрагмента, но не правильность толкования LLM. Подтверждение ожидаемого поведения требует review по требованию и повторного gVisor-прогона. Результат генерации не объявляется успешно выполненным тестом.

План не сохраняется частично после ошибки. Изменение проекта во время генерации отклоняет устаревший результат. Повторный анализ существующего плана не вызывает платную генерацию: редактирование доступно в Test Studio либо в новом проекте.

Для подтверждённой проблемы `patches.py` использует тот же адаптер. Сервер строит canonical diff и ограничивает изменения существующими implementation-файлами Python или JS/TS/JSX/TSX. Тесты, конфигурация, зависимости, HTML и новые файлы запрещены. Python проходит AST; JS/TS syntax/build и поведение проверяются в gVisor. До apply исходники неизменны; контрольный исходник, целевой модуль и полный сохранённый набор выполняются отдельно на том же image ID. Применение требует отдельного подтверждения конкретного patch SHA и verification UUID.

## Согласие и секреты

Перед каждой внешней операцией UI запрашивает preview: список файлов, исключения и обнаруженные редактирования, домен провайдера, модель и верхнюю оценку резерва. При генерации патча передаются также требование, review, код теста и traceback. В API требуется JSON body:

```json
{"consent":{"confirm":true,"project_state_sha256":"64 hex chars from preview","provider_fingerprint":"64 hex chars from preview"}}
```

Preview: `GET /api/projects/{id}/ai-context`; затем `POST /api/projects/{id}/analyze` или `POST /api/bugs/{id}/propose-fix`. Отсутствующее/отрицательное согласие — 428, устаревший проект/провайдер — 409. Согласие сохраняется с временем, проверяется повторно worker перед отправкой. Отмена диалога не создаёт AI-задание. PDF/DOCX извлекаются в worker, не во время HTTP-preview.

`.env`, скрытые пути, private-key files и пути oracle/ground-truth исключаются. В других строках удаляются распознаваемые API keys, токены, JWT, bearer credentials, пароли, connection strings, private keys и значения известных credential env. Контекст не обрезается незаметно: превышение лимита блокирует запрос. Источники с обнаруженным секретом полностью исключаются из patch-контекста; их изменение запрещено, чтобы `[REDACTED]` не заменил реальные байты проекта.

Это эвристический фильтр, не универсальный DLP. Нестандартные/непомеченные секреты и персональные данные могут быть не распознаны: проверяйте данные до согласия. `.env` никогда не отправляется. Инструкции в документах/коде считаются недоверенными данными; prompt injection не получает инструментов, команд или управления runner.

## Таймауты, повторы и расходы

Значения по умолчанию:

| Настройка | Значение | Действие |
| --- | ---: | --- |
| `LLM_CONTEXT_CHARS` | 40000 | Предел сериализованного контекста одного запроса |
| `LLM_MAX_OUTPUT_TOKENS` | 4000 | Лимит completion в запросе |
| `LLM_MAX_CALLS` | 4 | Общий предел попыток на задание; допустимо 1–6 |
| `LLM_MAX_JOB_TOKENS` | 120000 | Консервативный токеновый резерв на задание |
| `LLM_MAX_DAILY_TOKENS` | 1000000 | Общий резерв за UTC-день |
| `LLM_MAX_DAILY_CALLS` | 50 | Общие вызовы за UTC-день |
| `LLM_MAX_JOB_USD` | 1 | Верхняя оценка резерва задания по заданным тарифам |
| `LLM_MAX_DAILY_USD` | 20 | Аналогичный общий дневной резерв |
| `LLM_INPUT_USD_PER_MILLION` | 10 | Настраиваемый расчётный тариф входа |
| `LLM_OUTPUT_USD_PER_MILLION` | 30 | Настраиваемый расчётный тариф выхода |
| `LLM_TIMEOUT_SECONDS` | 40 | HTTP timeout, connect не более 10 с |
| `LLM_JOB_DEADLINE_SECONDS` | 160 | Контроль времени между попытками и во время чтения |

Укажите тарифы **не ниже актуальных тарифов выбранной модели**. Значения 10/30 — технические консервативные defaults, не заявление о текущей цене OpenAI. Денежный резерв — оценка при соблюдении провайдером output limit и заданных тарифов, не гарантия его счёта. Для строгого внешнего финансового ограничения дополнительно задайте provider-side spending limit. Неизвестный usage не считается нулём.

Перед каждой попыткой резервируется вход по UTF-8 bytes запроса с запасом и весь output limit. Повтор также расходует резерв; uncertain timeout не возвращает его. Дневная строка `ai_budgets` обновляется атомарным условным SQL UPDATE и разделяется всеми worker-процессами, переживает restart. Contract/live имеют отдельные счётчики. Увеличенные тестовые квоты задаются только test override.

До двух попыток на этап. Временные 408/409/429/500/502/503/504 и network/timeouts повторяются в оставшемся бюджете; 400/401 не повторяются. Короткий числовой Retry-After учитывается; задержка больше 10 с прекращает автоматический retry. Отказ модели, truncated finish reason, слишком большой ответ (>1 MB) и неожиданный transport error завершают операцию. Невалидная структура/связи/синтаксис могут получить одну повторную попытку с общей инструкцией исправить ответ, без публикации его содержимого.

Приложение проверяет deadline при admission и чтении; сетевой read timeout также ограничен. Это не отменяет удалённую операцию провайдера после client timeout. Общий Celery soft/hard timeout 240/270 с сохраняется.

## Журнал и статистика

`GET /api/projects/{id}/ai-statistics`, также Reports → «AI Engine · журнал генераций». Сохраняются этап, номер попытки, mode, model/provider, duration, status/error code, резерв и только числовой usage, если он предоставлен. Prompt, ответ, API key, provider error body и чувствительные значения не записываются в журнал. Worker логирует тип сбоя и job UUID без traceback содержимого. Анализ и патч используют единый формат аудита.

Успех означает структурно и семантически допустимый **ответ генерации**, не корректный тест или исправление. Ошибка селектора Playwright, syntax/collection/runtime failure, регрессия патча отражаются фактическим runner-результатом отдельно. В частности `strict mode violation` считается ошибкой теста и не может стать Confirmed.

## Контрольные проекты

Новые исходники: `evaluation/projects/python_dispatch` и `evaluation/projects/react_booking`. `evaluation/oracles.json` и `evaluation/oracle_tests/` отделены от загрузок. `tests/compose/novel_projects.py` загружает только файлы `projects/<name>`, читает oracle после генерации/исполнения. Oracle checks затем запускаются отдельно в gVisor, не отправляются Engine/провайдеру и не заменяют сохранённые AI-тесты.

```sh
docker compose -f docker-compose.yml -f compose.test.yml up --build -d --wait
python tests/compose/novel_projects.py
python tests/compose/ai_negative_smoke.py
python tests/compose/build_oracle_probe.py
docker compose exec -T supervisor python < work/oracle-probe.py
```

Contract provider выдаёт подготовленные JSON, а очередь, БД, проверка схем, Chromium/pytest, coverage, diff и gVisor-прогоны реальны. Эти результаты не измеряют автономную способность живой LLM находить незнакомые баги. С ключом `novel_projects.py --allow-external` разрешает отправку только этих контрольных проектов; после live-generation/run останавливается для пользовательского review. Полный review/fix/apply проходите через UI. Скрипт не применяет патчи автоматически.

Без ключа скрипт сохраняет `NOT_VERIFIED_API_KEY_MISSING`, число живых генераций 0, не обращается к платному endpoint и не подставляет контрактные данные. Фактический отчёт этого этапа — `validation-ai-engine.md`.

Обычные Compose smoke helpers отказываются автоматически подтверждать отправку в live-mode. Единственное исключение — явно запущенный evaluator с `--allow-external`; остальные контрактные проверки требуют test override.

Решения сверены с официальной документацией: [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat), [ошибки и retries](https://developers.openai.com/api/docs/guides/error-codes), [rate limits](https://developers.openai.com/api/docs/guides/rate-limits). Strict schema требует required полей и `additionalProperties=false`; дополнительно применяется локальная валидация.


## Совместимость реального провайдера и диагностика

Текущий live-протокол: `docs/live-ai-validation.md`. Исторические контрактные результаты не являются live-результатами.

`LLM_REASONING_EFFORT` — необязательный параметр (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`), передаваемый без изменения `LLM_MODEL`. По умолчанию поле не отправляется. Укажите только значение, которое поддерживает выбранная модель/провайдер. Оно входит в fingerprint согласия. При смене требуется новое согласие на новый workflow.

Для шлюзов доступен существующий `LLM_RESPONSE_FORMAT=json_object`: JSON Schema включается в инструкцию, а локальные Pydantic-валидация, известные связи требований, их неизменность и синтаксическая проверка остаются обязательными. В режиме `json_schema` схема передаётся также через response_format. Приём API-параметра не доказывает, что сторонний шлюз действительно выполняет constrained decoding.

Журнал теперь сохраняет безопасные категории отказов: авторизация, квота/баланс, модель/endpoint, формат запроса, rate limit, соединение/таймаут и техническая ошибка. Произвольный текст provider error не копируется в журнал. HTTP-ошибка читается с ограничением 16 KiB только для allowlisted классификации. Для ошибок структуры сохраняются только типы Pydantic и фиксированные семантические причины, без input/context/messages с исходниками. Причина включается в ограниченный повторный запрос.

`response_model` фиксирует идентификатор из ответа. Неожиданная смена модели отклоняется (допускается snapshot с тем же префиксом выбранного ID). Если провайдер не сообщает model, журнал не приписывает ему доказанную модель. Сторонняя маркировка не доказывает происхождение inference криптографически. Клиент не выбирает запасную модель другого производителя. Если ответ повторяет действующий API-ключ, он отклоняется до сохранения кода или передачи в runner.

Gherkin-проверка распознаёт заголовки Feature, Scenario/Example, Scenario Outline/Template и соответствующие русские варианты. Это проверка заголовков, не полный Cucumber parser. Каждый сценарий должен быть самодостаточным; исполняемый pytest/Playwright не переписывается для зелёного результата.

Контекст исправления включает документированные требования и реальные падения сохранённого тестового набора. Это помогает не ограничивать модель одним assertion при нескольких ошибках. Приватные oracle и эталонные исправления туда не добавляются. Source SHA, запрет изменения тестов/зависимостей, gVisor verify и отдельное подтверждение apply сохранены.

Повторяемый небольшой smoke запускается только явно из доверенного backend:

```sh
docker compose exec -T api python - --allow-external < scripts/live_smoke.py
```

Он использует только синтетическое сложение, один запрос, штатные бюджет/таймаут/валидацию и не исполняет полученный код на backend. Исполнение производится отдельно через обязательный gVisor runner. Не используйте эту команду как замену независимому benchmark.


`LLM_TEST_REVIEW=1` включает проверку нового плана по документу до сохранения и первого исполнения. Reviewer получает требования и новый план, но **не исходную реализацию, результаты runner или oracle**. При отклонении разрешена одна повторная генерация с замечаниями и одна повторная проверка; повторное отклонение завершает анализ ошибкой без сохранения частичного плана. Старые проекты/тесты не меняются. Это дополнительная проверка той же LLM, не независимый oracle и не гарантия корректности.

Review использует до 512 выходных токенов. Для полного extract → generate → review → regenerate → review может потребоваться `LLM_MAX_CALLS=6`; общие ограничения USD/токенов/дедлайна по-прежнему действуют, при их исчерпании анализ останавливается. В журнале сохраняются только approved и число замечаний. В `compose.test.yml` review явно выключен для существующих контрактных фикстур. Доказательство Bug Proof и применение патчей эта проверка не подтверждает.

### Планирование Playwright до просмотра реализации

Для JS/TS при `LLM_TEST_REVIEW=1` контракт ожиданий составляется в запросе извлечения требований: extract + acceptance contract → generate → review. Модель составляет конкретные действия и ожидаемые постусловия только из извлечённых требований, без исходников. Контракт ограничен 24 пунктами и общим лимитом ответа; ссылки должны покрывать ровно известные ключи требований. Тот же неизменный контракт передаётся генератору, reviewer и единственной допустимой повторной генерации до сохранения. Результаты выполнения и приватные oracle в этот цикл не поступают.

Генератору рекомендованы отдельные Playwright-кейсы с уникальными буквальными именами, конкретными входами и точными селекторами. Это устраняет необходимость хрупкой параметризации в небольших наборах. Документ остаётся источником ожидаемого поведения. Контракт — результат LLM, поэтому он также может ошибаться; это не независимый oracle. При исправлении тесты уже выполненного набора не переписываются.

Полный JS-цикл с одной коррекцией занимает до 5 запросов без транспортных повторов. Рекомендуется `LLM_MAX_CALLS=6`; существующие лимиты времени, токенов и стоимости не увеличиваются автоматически. Для экономного отдельного live benchmark: `python tests/compose/benchmark.py --allow-external --project react_booking --output work/js-benchmark.json`. Без `--project` проверяются оба контрольных проекта. Согласие этой команды распространяется только на синтетический evaluation-корпус.

Отклонённые валидированные черновики и замечания reviewer сохраняются как `generation_review` в записи анализа проекта, включая остановку по дедлайну или бюджету. Это данные проекта для разбора ошибки, не исполняемые test-cases. Privacy-фильтр применяется повторно. В общих AI-логах и ai-statistics по-прежнему нет исходников, текста замечаний и ответов. Доступ к черновикам требует тех же мер защиты локального приложения, что и доступ к исходникам и принятым тестам.

Если reviewer ошибается, доступен явный `POST /api/projects/{pid}/accept-ai-draft`: `confirm`, `analysis_id`, `draft_index`, `draft_sha256`, `project_state_sha256`, `reviewer_note`, `reviewer_kind` (`human` или `agent`). SHA черновика — SHA256 UTF-8 `json.dumps(plan,sort_keys=True,ensure_ascii=False)`. Принимаются только серверные черновики завершённого неуспешного анализа, без нового кода от клиента. Состояние должно совпадать с исходным согласием; активное задание, существующий план, чужой анализ и неверный SHA блокируются. Повторяются структурная проверка и проверка профиля. Исходная ошибка анализа сохраняется, новый факт проверки имеет operation `accept_draft`, тесты — origin `llm-reviewed-draft` с provenance. Это API-маршрут, отдельная кнопка UI пока не добавлена. Автоматического обхода reviewer нет; агентская проверка явно отличается от человеческой и от одобрения самой LLM. Это не подтверждение применения патча.

В patch-context полные редактируемые исходники и документированные требования сохраняются, а повторяющиеся тестовые программы/логи заменены SHA, именами упавших кейсов и явно обозначенными diagnostic excerpts. Приватные oracle не добавляются. Полный неизменённый набор и исходные traceback остаются в серверном снимке и используются при replay/verify. Сокращение контекста не сокращает регрессионную проверку.

## Автономный QA и layered validation

Новый обязательный многоуровневый путь используется кнопкой «Автономный QA» и `POST /api/projects/{id}/autonomous` с обычным `consent` на весь явно обозначенный цикл. Подробный протокол, классификации, ограничения, текущий частичный live-результат: [autonomous-ai-validation.md](autonomous-ai-validation.md). Старый отдельный AI-анализ и его review совместимы с прежним режимом; их результаты не объявляются автономной сертификацией.

`services/ai/validation.py` выполняет статический preflight, фиксированный gVisor `phase=validate` (AST/esbuild и pytest collect-only / Playwright list), структурированную смысловую оценку каждого assertion и максимум одну отдельную adjudication на каждую версию плана. Отмена отказа требует точных цитат утверждения reviewer, документа и кода. Разрешена максимум одна коррекция до первого исполнения. Неоднозначность терминальна: `manual_review_required`. Missing/ambiguous locator не подтверждается как дефект автоматически.

В автономном режиме список требований присоединяется сервером: генератор отвечает schema `scenarios`, а requirement/framework ограничены enum. Весь цикл делит один исходный бюджет AIAdapter и дедлайн; operation output caps только снижают пользовательский максимум. Проверка, выполнение, proof и verify закреплены за SHA состояния/плана/теста и образом runsc. Автоматическое proof помечается `automated_validation`, без фиктивного подтверждения человеком. Apply не вызывается.


### Проверка готовности MVP

[Python live и текущая готовность](mvp-readiness.md): последний scenario-only протокол прошёл реальную генерацию, review, Bug Proof и Fix & Verify без ручного принятия. Локальный разбор JSON дополнительно использует `strict=True`, без преобразования строк/boolean/float в integer-индексы review. Ужесточение отдельно проверено offline на сохранённых live evidence и контрактными E2E; после этой однострочной правки новый платный цикл не запускался.
