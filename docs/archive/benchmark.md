## Что изменилось

- Test Planner v2 отклоняет генерацию, если хотя бы одно извлечённое требование осталось без исполняемого сценария. Такие ответы проходят ограниченный retry адаптера, затем задание завершается ошибкой без частичного сохранения плана.
- Checklist требует рассматривать границы и соседние значения, документированные типы/форматы, исключения, все поля состояния, бизнес-инварианты, сочетания параметров, негативные сценарии и авторизацию при наличии её в требованиях. Для непрописанного поведения не задаётся произвольный ожидаемый ответ.
- Каждый сценарий сохраняет ключ требования, Gherkin и метки dimensions. Извлечение по-прежнему требует точную цитату документа; требования не меняются между этапами. Метки dimensions не считаются доказанным семантическим покрытием.
- `services/ai/quality.py` вычисляет диагностику из наблюдений gVisor: line/branch coverage, требования с исполнившимися assertions, непроверенные требования, исполняемость модулей и ошибки инфраструктуры. `quality_inputs` фиксируется при постановке задания; последующая правка Test Studio не меняет старую оценку. Доступно в `GET /api/runs/{id}` → `quality`. Модуль с одновременно нормальными и ошибочными кейсами учитывается как частично исполнившийся; успешный кейс не скрывает сломанный.
- Количество тестов не превращается в главный показатель или составной балл. Нет измерения / нет ветвей — ratio `null`. Assertion-падение может упражнять требование, но не доказывает правильность самого assertion; проходящий кейс не доказывает полноту всех пунктов требования.

## Анализ двух ранее пропущенных ошибок

1. **PY-PICKUP, R4:** при pickup=true и weight=200 ожидалось 0, фактически было 700; с priority=true ожидалось 300, фактически 1000. Требование извлекалось, но сценария R4 не было. Новая контрактная фикстура проверяет 199/200/201 и порядок применения pickup + priority. На одно-дефектной версии падают два кейса одного дефекта — это не два обнаруженных дефекта.
2. **TS-RESET, R3:** после ввода 2 и сброса поле сохраняло 2 вместо 1. Ранее не проверялось восстановление всех полей состояния. Новый сценарий проверяет остаток, quantity, сообщение и повторный reset.

Сохранённые проекты и тесты прошлых запусков не изменялись. Для новых запусков контрактный provider намеренно получил новые подготовленные ответы. Это проверяет транспорт, сохранение плана, исполнение и оценку, но само по себе не доказывает улучшение рассуждений LLM.

При ревью новой Python-фикстуры удалены два assertion на HTTP 422 для нечислового/нецелого формата: документ явно задавал этот код только для перечисленных числовых ограничений. Python workflow и независимая оценка повторены с исправленной фикстурой; требования проекта не менялись. Неуточнённый контракт формата требует уточнения документа, а не выдуманного ответа в тесте.

## Как устроена независимая оценка

В AI загружаются только файлы `evaluation/projects/python_dispatch` или `react_booking`. `evaluation/oracles.json`, `variants.json` и `oracle_tests/` находятся отдельно и не копируются в backend-образ. Скрипт читает приватные данные только после генерации. Privacy filter дополнительно исключает oracle/ground-truth пути. Ответы oracle никогда не добавляются в prompts.

После генерации **неизменные** тесты исполняются на исправленном эталоне, двух версиях с отдельным дефектом и одной дополнительной мутации каждого проекта. Перед зачётом обнаружения нужен проходящий эталон, одинаковые test/case identities, SHA тестового набора и image ID, нормальное завершение gVisor и assertion-падение варианта. Приватные oracle должны пройти эталон и дать ровно один провал на соответствующем одно-дефектном варианте. Ошибки запуска, skipped, изменённые кейсы и проваленный эталон не считаются обнаружением или убитой мутацией.

`missed` включает все незачтённые известные дефекты; `unassessable` показывает подмножество, которое нельзя оценить из-за невалидного исполнения/контроля. Ложные сообщения оцениваются по assertion-падениям на исправленном эталоне, отдельно от инфраструктурных ошибок. Дедупликация дефектов выполняется по приватным ID и одно-дефектным вариантам, а не по числу failed.

## Live readiness: отдельный безопасный запуск

Приложение не требует ключ для старта. После возврата в обычный Compose фактический запуск benchmark с `--allow-external` без ключа завершился:

```json
{"status":"NOT_VERIFIED_API_KEY_MISSING","projects":0}
```

CLI запускается из корня репозитория в Python-окружении с установленным `requirements.txt` (Windows: `.venv\Scripts\python.exe`).

Настройте `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в локальном `.env` по `docs/ai-engine.md`, не коммитьте ключ. Обычный Compose: `docker compose up -d --remove-orphans --wait`. При изменении `.env` Compose обновит окружение API / worker. Отдельный запуск:

```sh
python tests/compose/benchmark.py --allow-external --output work/benchmark-live.json
```

Сначала просмотрите `evaluation/projects/`: флаг — явное согласие передать только эти контрольные исходники и требования настроенному провайдеру. Ни приватный manifest, ни oracle не отправляются. Без флага live-отправка блокируется до создания проектов. Скрипт не включает stub автоматически и сохраняет режим каждого workflow. Внешний ключ не передаётся в gVisor.

В live-режиме генерация и дифференциальные прогоны выполняются автоматически; подтверждение ожиданий Bug Proof остаётся человеку. Проект ID сохраняется в JSON. После review, повторного доказательства, предложения и проверки патча в UI можно дополнить тот же отчёт:

```sh
python tests/compose/benchmark.py --resume-report work/benchmark-live.json --output work/benchmark-live-reviewed.json
```

Resume только читает API и запускает контрольные проверки в gVisor; не отправляет LLM-запросы, не подтверждает и не применяет патч. Исходники и тесты обязаны соответствовать исходному снимку. Применение всегда отдельным явным подтверждением. Пока review/verify не выполнены, live proof/fix отмечены как pending/непроверенные, а не успешные. Исходники менять не нужно.

Для контракта: `docker compose -f docker-compose.yml -f compose.test.yml up --build -d --wait`, затем `python tests/compose/benchmark.py`. Вернитесь к обычному Compose после теста. На Windows команды Docker выполняются через WSL Ubuntu; evaluator делает это автоматически для контроллера.

## Ограничения и найденные проблемы

- **Живых генераций: 0. Эффективность настоящей LLM не оценена.** Нужны ключ и отдельная серия blind-прогонов; подготовленные ответы не заменяют её.
- Корпус состоит из двух небольших уже известных контрольных приложений и четырёх известных дефектов. Новые экземпляры этих приложений не являются новым holdout-корпусом; автор контрактных ответов знает спецификацию. Oracle отделены от AI-контекста, но для оценки обобщения нужна существенно более широкая независимая выборка.
- Проверка наличия сценария на каждое требование не гарантирует полноту assertions и корректность их трактовки. Dimensions — заявления генератора. Исключения/авторизация не добавляются к этим проектам, где они не документированы.
- Один assertion может скрыть последующие проверки в том же кейсе. Контрольные параметризации частично уменьшают этот эффект; semantic coverage всех пунктов автоматически не доказан.
- Фиксированные зависимости runner, лимиты контекста/выходных токенов/времени и 40 модулей ограничивают большие планы. План с недостающими требованиями отклоняется, а не выдаётся за полный. Произвольный npm/pip install и сеть не разрешены.
- Полная регрессия требует зелёного сохранённого набора. Частичный патч одного из нескольких независимых дефектов может не пройти verify, пока другой дефект остаётся. Это намеренный консервативный результат, не повод ослабить assertions.
- Автоматические Bug Proof review в контрактном скрипте относятся только к синтетическим фикстурам. В live-режиме такой review не подставляется.
- Общий fake-provider успех JSON не означает валидный тест. Старый неоднозначный React selector и ранее пропущенные два дефекта сохранены в истории `validation-ai-engine.md`; новое review также обнаружило и удалило недокументированные форматные assertions.
- CI workflow дополнен benchmark-командой, но удалённый CI в этой сессии не запускался. В этом этапе проверены локальные backend/E2E/Compose и реальные benchmark-прогоны; старые security/resource probe логи относятся к предыдущему этапу, runner policy с тех пор не менялась.
