# Дебагыч: проверка настоящей LLM

> Исторический протокол предыдущей серии из 31 запроса. Более новая JS/TS серия, её успешные проверки и ограничение автономности описаны в [js-live-workflow.md](../js-live-workflow.md). Старые неудачные запуски ниже сохранены.

20 октября 2026, Asia/Tomsk. Локальный Docker Compose / WSL2 / gVisor.

**Главный результат:** реальная `gpt-6-luna` сгенерировала pytest-набор, независимо выявивший оба дефекта Python-контроля; Bug Proof воспроизведён, модель предложила diff, проверка кандидата и регрессия прошли в gVisor. **JavaScript/TypeScript live workflow пока не доведён до надёжного состояния. Общего результата 4/4 нет: зачтено 2/4 известных дефектов.** Патчи live-проектов не применялись.

## Провайдер и конфигурация

- Base URL: `https://triklz27.ru/v1`, сторонний OpenAI-compatible провайдер, выбранный пользователем.
- Запрошенный ID: **`gpt-6-luna`**; в завершённых ответах с полем model получен тот же ID. Модель не заменялась; Claude/Gemini/DeepSeek и другие производители не вызывались.
- `/models`: HTTP 200, выбранный ID присутствует, `owned_by=openai`. Этот ID присутствует в [официальном каталоге OpenAI](https://developers.openai.com/api/docs/models/gpt-6-luna). Эти проверки подтверждают настройки и метаданные; криптографически доказать, какая модель находится за сторонним шлюзом, они не могут.
- API и Celery получили переменные из локального `.env`; контейнеры пересозданы. Успешные extraction/generation/patch операции выполнены настоящим worker, не stub.
- Ключ не печатался. `.env` исключён `.gitignore` и `.dockerignore`; в source ZIP он не включён. Ключ не передаётся в sandbox. Параметры key/base URL/model пользователя сохранены.
- Для совместимости изменены только дополнительные настройки: timeout 40→60 s, `LLM_RESPONSE_FORMAT=json_object`, `LLM_REASONING_EFFORT=none`; позже включён `LLM_TEST_REVIEW=1`, max calls 4→6. Максимум 120000 резервируемых токенов / $1 на job, общий deadline 160 s и дневные 50 calls / 1000000 reserved tokens / $20 не увеличивались. Review имеет меньший выходной лимит 512 tokens.

Первый smoke использовал `json_schema`: API принял запрос, ответ прошёл локальную схему. Это не доказывает, что прокси реализует все ограничения JSON Schema. Полные планы сначала давали ошибки валидации/таймауты; `json_object` проверен как вариант совместимости. В нём схема явно включена в инструкцию, а Pydantic, ссылки и неизменность требований, ограничения полей и синтаксическая проверка остаются обязательными. Серверная constrained decoding в этом режиме не заявляется. См. [официальное описание различий JSON mode и Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat).

**9 анализов новых экземпляров контрольных проектов: 2 завершены, 7 отклонены.** Один из двух сохранённых наборов оказался неисполняемым (JS). Это не серия независимых holdout-проектов: это повторные попытки на двух небольших контрольных приложениях. Эти числа нельзя выдавать за общую вероятность успеха модели.

Первоначальная причина первого invalid_structured_response не была детализирована старым журналом; не восстанавливаем её предположением. После добавления диагностики зафиксированы конкретные Gherkin-отказы. Старый валидатор действительно отвергал стандартный `Scenario Outline:`: проверял только буквальную подстроку `Scenario:`. Теперь распознаются Outline/Template, Example и русские заголовки; prompt требует самодостаточный Feature для каждого сценария. [Cucumber определяет эти формы как допустимые](https://cucumber.io/docs/gherkin/reference/). Это исправление обработки Gherkin, не изменение assertions для зелёного результата. Проверка заголовков не заменяет полный Cucumber parser.

Для JS фактически наблюдался сборочный сбой: object-деструктуризация применялась к array-строкам, quantity становилось undefined, названия тестов дублировались. При чтении сохранённого тестового кода дополнительно выявлены неправильные ожидаемые значения reset (2/0 вместо документированного 1) и потенциально неоднозначный `getByRole('status')` при наличии output. Последние ошибки нельзя считать исполненными продуктовым runner: сборка остановилась раньше.

Старые неудачные проекты и их тесты не редактировались. Повторные генерации создавали новые проекты. В новой opt-in проверке план рассматривается **до первого исполнения**, по требованиям и самому плану, без исходной реализации, фактических результатов или oracle. При замечаниях разрешена одна повторная генерация и один повторный review; повторный отказ блокирует сохранение. Журнал хранит approved и количество замечаний. Это проверка той же моделью, может ошибаться и не является независимым доказательством качества. Её live-испытание на JS закончилось отказом, а не успехом генератора; точное содержание последних замечаний не журналировалось.

## Python Bug Proof и Fix & Verify

1. Реальная модель извлекла требования, подготовила Gherkin (включая Scenario Outline) и четыре pytest-модуля.
2. Тесты дали 12 passed / 3 failed. Независимая оценка отнесла три падения к двум дефектам; на правильном reference все 15 кейсов проходят.
3. Агент разработки в рамках пользовательского разрешения на синтетический workflow сверил неизменённый assertion с **публичным документом**: weight=1000 должен стоить 700 RUB. Это не автоматическое подтверждение по заявлению модели и не утверждение, что человек нажал кнопку. Штатный API review вызван явно, затем Bug Proof повторил исходный набор в чистом gVisor.
4. Настоящая модель предложила минимальный diff реализации. Контекст патча включает документированные требования и реально падающие модули сохранённого набора; скрытые oracle и правильные исправления туда не входят. Тесты, требования и зависимости менять запрещено.
5. Baseline / focused / полная regression выполнены в gVisor. Кандидат получил 15/15 и независимые 4/4 oracle. Полная корректность приложения за пределами этих проверок не доказана.
6. `confirm=false` с настоящими fix/verification/SHA был отклонён HTTP 409. ZIP оригинала и тесты не изменились. **Apply не выполнялся.**

Пересборка окружения в ходе доработки сменила image ID. Попытка повторного evaluator на старой привязке закономерно была отклонена image guard; её JSON сохранён. Защита не отключалась. Неизменённый набор повторно запущен на текущем image, review/replay и live-предложение/verify повторены; итоговые цифры выше относятся к одной привязке текущего образа. В истории поэтому **два настоящих LLM-предложения и две успешных проверки одного и того же Python-проекта**, а не два независимых успешных проекта. Старые результаты не удалены.

## Регрессия и безопасность

- **138 backend tests passed** (одно upstream предупреждение Starlette/AnyIO). Проверены новая диагностика без body/input, запрет эха ключа, модель из ответа, опциональный reasoning, корректный Outline/русский Gherkin и doc-only review/correction до любого исполнения.
- **9 E2E passed**, 2.1 min, после всех изменений. Это явно **contract-test provider**, реальные PostgreSQL/Celery/gVisor/браузер, не дополнительный live benchmark. Один Shop-тест намеренно ожидает assertion-падение и засчитан как expected failure.
- Дополнительный настоящий gVisor `fix_verify_smoke.py` с контрактным transport прошёл: исходник/кандидат/регрессия, отказ регрессионного патча, отказ устаревшего состояния, неизменность тестов и apply только после явного подтверждения.
- Python security probes прошли: uid, secrets/socket/mounts, readonly root, capabilities, network denial, NPROC, OOM, timeout, cleanup. Playwright security probes прошли: настоящий Chromium, отсутствие ключей/сокета/host IPC, сеть запрещена, readonly root, лимиты и stuck-worker deadline/cleanup.
- Runner policy не ослаблялась. Не было runc fallback, сети/установки зависимостей из проектов, host execution загруженного/генерированного кода, передачи LLM-запросов в sandbox или автоматического apply.
- LLM-операции выполнялись только доверенным backend. Отправлялись только синтетические контрольные проекты; пользователь дал разрешение в ТЗ. Согласие фиксируется штатным API fingerprint/state hash. Правки параметров приводили к новым согласиям для новых jobs.
- `docker compose config --quiet`, пересоздание API/Celery и healthchecks проверены. В конце возвращён обычный Compose с настоящим ключом и выбранной моделью; stub удалён. Приложение: http://127.0.0.1:8080/.

## Известные ограничения и необходимые дальнейшие действия

1. **Полный live JS/TS workflow не подтверждён.** Нельзя считать его готовым по зелёным контрактным E2E. Нужна дальнейшая работа над типовой параметризацией, уникальностью titles, локаторами и соответствием ожидаемых состояний документу; старые неудачные наборы нельзя править ради зелёного результата.
2. `LLM_TEST_REVIEW` с той же LLM — дополнительный фильтр, может пропускать ошибки или ошибочно отклонять корректное. Замечания не журналируются текстом, доступны verdict и count. Последний JS job отвергнут после ограниченного повторного review; успешная новая JS-генерация не заявляется.
3. После добавления review-gate живое создание **нового Python-плана с включённым gate** не повторялось: существующий реальный корректный набор повторно проверен без изменения. Gate отдельно испытан unit-тестом и отрицательным live JS-сценарием. Его нельзя объявлять доказанным улучшением генерации на всём корпусе.
4. Провайдер нестабилен по задержке и дал 502. Интерактивный latency и надёжность недостаточны для обещания автономной обработки любого проекта; модели/провайдера без согласования не меняли. После этих ограниченных серий новые внешние испытания прекращены, а не запускались бесконечно. При дальнейшем испытании нужны отдельный budget и контроль latency/usage.
5. Корпус маленький: два приложения, четыре заложенных дефекта. Обобщение на незнакомые большие проекты не доказано. 100% coverage не означает отсутствие ошибок; seeded mutation всего одна допустимая Python-мутация.
6. Полная regression консервативно требует зелёного набора. Ложный assertion или другой неисправленный дефект блокирует verify; ожидаемые значения не подгоняются под текущую реализацию. Изменение image ID требует нового baseline/проверки; guard сохраняется.
7. Происхождение inference за сторонним proxy подтверждено только каталогом/метаданными ID, не независимой аттестацией OpenAI. Billing и расход девяти незавершённых ответов неизвестны.
8. Удалённый CI в этой сессии не запускался. Все перечисленные прогоны — локальные; контрактные и live evidence разделены.
