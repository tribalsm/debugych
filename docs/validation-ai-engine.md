# AI Engine: фактический отчёт

Дата: **20 октября 2026, Asia/Tomsk**. Проверено в существующем репозитории Дебагыча на Windows/WSL2, Docker Compose, PostgreSQL, Redis, Celery и gVisor.

## Статус главной цели

**Живое AI-тестирование НЕ ПРОВЕРЕНО. API-ключ недоступен.** В окружении процесса ключа нет, рабочего `.env` нет, обычный backend сообщает `configured=false`, `missing_LLM_API_KEY`, `mode=live`. Запуск live evaluator сохранил `NOT_VERIFIED_API_KEY_MISSING`, 0 живых генераций, 0 попыток отправки платному endpoint. Нельзя сделать вывод о способности настоящей LLM находить незнакомые дефекты или о совместимости конкретного живого провайдера.

Реализована и проверена вся интеграционная инфраструктура с **явно контрактным провайдером**. Его подготовленные ответы не выдаются за inference. Сборка проектов, очередь, БД, pytest/Chromium, coverage, Bug Proof, diff, регрессии, скриншоты и применение тестовых патчей в E2E — реальные.

## Аудит и изменения

Исходная реализация имела два дублированных `httpx.post`, JSON object с локальной проверкой, общий 90-секундный timeout и повтор на любые ошибки. Контекст анализа молча обрезался; общего дневного бюджета, учёта usage, фильтра секретов и серверного согласия не было. Исправления JS/TS блокировались.

Теперь используется единый адаптер с strict JSON Schema, локальной структурной/семантической проверкой, bounded response stream, отказом на truncation/refusal, классифицированными retries и таймаутами. Отдельное извлечение требований проверяет source/quote, следующий этап генерирует связанный план по структуре кода. Сохранены источники требований. Текст требований не меняется при построении плана. Контекст не обрезается незаметно.

Согласие проверяется API и worker по raw project hash и provider fingerprint, сохраняется с временем. Известные секреты редактируются, `.env`/private-key/oracle пути исключаются. Sensitive source не может быть заменён очищенной версией через patch. Логи/audit содержат безопасные метаданные, не prompt, ответ, ключ или provider error body. Дневные admission reservations атомарны и сохраняются в PostgreSQL (`003_ai_budgets`).

Общий Fix & Verify расширен на существующие JS/TS implementation-модули. Проверяются baseline, неизменённый целевой модуль, полный неизменённый план и source/test/patch hashes. Syntax/build JS проверяются в gVisor. Серверный diff, защита конфигурации/тестов и отдельное apply-подтверждение сохранены.

## Новые независимые исходники и известные пропуски

Проекты созданы отдельно от прежних Shop/calc/Counter fixtures. Engine получает только `evaluation/projects/<name>`: приложение и документ требований. `evaluation/oracles.json` и `oracle_tests/` остаются у evaluator, читаются после генерации и не отправляются модели. Описания/расположения дефектов не добавлялись в prompts. При контрактном провайдере это **не эксперимент с неизвестными багами для настоящей модели**: ответы провайдера подготовлены для проверки протокола.

| Проект | Проверенный первичный дефект | Что осталось после проверенного кандидата |
| --- | --- | --- |
| FastAPI Dispatch Quotes | weight=1000: 1100 вместо 700; кандидат делает границу включительной | pickup=true, weight=200: 700 вместо 0; R4 не покрыт подготовленным планом |
| React/TS Seat Desk | Бронирование всех 6 мест отклоняется; кандидат разрешает весь остаток | reset не возвращает quantity к 1; R3 не покрыт подготовленным планом |

Итого независимые проверки подтверждают **2 исправленных и 2 оставшихся дефекта** из 4 заложенных. Не называем их «пропущенными живой LLM»: живого прогона нет. Результат 3/3 generated tests не доказывает полную корректность — oracle непосредственно обнаруживает оставшееся нарушение в каждом кандидате.

## Ошибки, обнаруженные по ходу работы

Первый подготовленный React test plan использовал `getByRole('status')`. Он находил и output, и сообщение: runner показал strict-mode violation. Сохранённые тесты этого проекта **не изменялись** для получения зелёного результата. Шаблон контрактного провайдера для новых проектов получил однозначный selector с тем же ожидаемым текстом. Первоначальный ручной oracle имел ту же ошибку селектора и был исправлен до окончательных независимых измерений.

Engine/harness теперь классифицируют `strict mode violation` как ошибку теста, не product defect; такие кейсы запрещают Confirmed. Добавлен regression unit-test. Исходный ошибочный прогон сохранён в `initial-selector-error.json`. Это реальная ошибка подготовленного тестового плана, **не ошибка живой LLM**.

Новый E2E также выявил гонку в самом тесте диалога согласия: второй обработчик регистрировался до закрытия первого диалога. Проверка исправлена ожиданием завершения отказа. Фильтр секретов дополнительно проверен на длинном однословном входе и незакрытом private-key блоке; потенциально затратные regex-шаблоны ограничены. Финальные результаты приведены после этих исправлений.

## Ограничения и следующий живой прогон

Нужен пользовательский API-ключ и поддерживаемый model/endpoint. Установите три основные переменные и тарифы/лимиты по `ai-engine.md`, перезапустите API/worker, проверьте `/api/ai/status`. Перед каждым анализом/патчем подтвердите отправку очищенных данных. Для live control run можно использовать `novel_projects.py --allow-external`; затем review, patch/verify и отдельное apply через UI. Автономная оценка качества модели остаётся непроверенной.

Фильтр секретов эвристический; проверка данных до согласия обязательна. Поддерживаются фиксированные Python/Playwright dependency profiles; произвольный npm/pip install, Node backend, source-map coverage и Java execution не добавлялись. Большой context/replacement может не поместиться в бюджет; возвращается ошибка без скрытого сокращения. Нет автоматического исправления семантически неверного теста после выполнения; старый план сохраняется для анализа. Требования с цитатой всё ещё требуют проверки смысла человеком. Отчёты из недоверенного контейнера — наблюдения, не формальное доказательство.

Сетевой доступ sandbox не открывался, credentials туда не передаются. Патчи реальных пользовательских проектов не применялись. E2E применял только свою созданную синтетическую fixture после отдельного диалога. Удалённый GitHub CI не запускался; workflow дополнен воспроизводимыми проверками.
