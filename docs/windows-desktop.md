# Дебагыч для Windows

Основное приложение с собственным окном Tauri 2 / Windows WebView2. Это не Desktop Pet и не ярлык, открывающий обычную вкладку браузера. Используется тот же production frontend, FastAPI, БД, AI Engine и обязательный gVisor.

## Запуск

1. Распакуйте `debugych_windows_app.zip` в постоянную папку, например `Документы/Debugych`.
2. Запустите **Debugych.exe**. Папка `resources` должна оставаться рядом.
3. Приложение покажет подключение к backend и откроет рабочую область в собственном окне. Терминалы открывать не требуется.

Node установленной системы и npm для запуска не нужны: runtime включён в комплект со своей лицензией. Требуется Windows WebView2 Runtime. На этой машине он уже используется Desktop Pet. Пакет portable, не подписан сертификатом издателя и не является MSI-инсталлятором. Не обходите предупреждения Windows; корпоративная установка может требовать разрешения администратора.

## Автоматический backend

Приложение сначала проверяет настоящий `/api/health` и готовность gVisor. Здоровый backend переиспользуется, без перезапуска контейнеров. Для WSL Ubuntu приложение удерживает собственную скрытую сессию.

Если API недоступен, встроенный bootstrap:

- Проверяет Linux Docker и зарегистрированный runsc.
- Ищет существующий Compose backend, которому принадлежит loopback-порт 8000, включая остановленные контейнеры.
- Запускает только сервисы этого проекта в порядке postgres/redis, runner/supervisor, api, worker. Существующие volumes и серверная конфигурация не заменяются.
- Если готового стека нет, использует backend из комплекта и существующий docker-compose.yml. Создаётся отдельная серверная `.env` без LLM-ключа в каталоге данных приложения. Выполняется обычный `compose up -d --no-recreate --build`.

Первый запуск нового стека может занять несколько минут и требует скачивания обычных Docker/npm/pip зависимостей. Платный AI-запрос при запуске не выполняется.

Для локального QA на компьютере заранее должны быть настроены **WSL2 Ubuntu + Linux Docker + gVisor/runsc**, либо доступен Linux Docker через установленный Docker CLI. Приложение автоматически запускает готовые компоненты, но не устанавливает WSL и gVisor с повышенными правами, не перезапускает Docker ради установки и не отключает изоляцию. При отсутствии зависимостей будет экран ошибки с настройками и повтором, а не ложный успешный запуск. Без ключа доступны импорт, сохранённые результаты, demo и существующие тесты; AI недоступен явно.

## Настройки и будущий сервер

В меню окна **Подключение** можно выбрать:

- Локальный backend: по умолчанию `http://127.0.0.1:8000`.
- Backend на сервере: HTTPS origin без API-ключа, пути и пароля в URL.

После сохранения приложение переподключается. Ключ AI-провайдера остаётся на backend. Для серверного режима локальные контейнеры не запускаются. Сетевой запрос идёт через небольшой встроенный proxy с обычной проверкой TLS; сертификаты не отключаются.

Будущий перенос на сервер отдельно требует развёртывания и пользовательской авторизации. Эта локальная конфигурация не объявляется публичным SaaS. Настройка HTTPS-клиента подготовлена, но реальный удалённый production backend пока не развёрнут и не проверен.

## Данные и завершение

Настройки соединения находятся в `%APPDATA%/local.debugych.desktop/connection.json`. Локальные диагностические журналы и пример backend.env находятся в каталоге данных этого приложения. Ключи и содержимое `.env` не записываются в frontend bundle или release ZIP.

Закрытие приложения завершает только его собственный frontend-процесс и WSL keepalive. Общие контейнеры и БД командой stop/down не останавливаются. Повторный запуск фокусирует уже открытое окно через single-instance механизм. Desktop Pet продолжает обращаться к тому же backend на 8000; его web-ссылки могут по-прежнему открывать обычный браузер по настроенному адресу.

Внутренний loopback-порт выбирается один раз и сохраняется в `frontend-port.txt`. Благодаря стабильному origin сохраняются настройки веб-интерфейса и выбранный проект между перезапусками. Если порт занят посторонним процессом, приложение сообщает об этом, а не завершает чужой процесс.

## Реализация

- Native host: `apps/desktop`, отдельный идентификатор и процесс Debugych.exe.
- Встроенный frontend: существующий `apps/web/dist`, без переписывания страниц.
- Backend bootstrap: `scripts/ensure-backend.ps1`, встроен в native host; фиксированный код и отдельные параметры окружения, без изменения Windows ExecutionPolicy.
- HTTP proxy: существующий `scripts/serve-web.mjs`, loopback и собственный свободный порт. HTTPS upstream допускается только при явном выборе серверного режима.
- Packaging: `scripts/package-windows-app.py`. В архиве нет `.env`, БД, user settings или истории Desktop Pet.

Проверки и фактические ограничения конкретной сборки записаны в `outputs/web-integration/desktop-validation.json`. Полный холодный запуск с нуля нельзя считать подтверждённым по одному подключению к уже работающему API. Порядок запуска существующих сервисов дополнительно проверяется fixture-тестом без воздействия на общий стек.

Сборка из исходников на Windows с Rust MSVC, C++ Build Tools, Node и Python: `scripts/build-windows-app.ps1`. Python и Rust нужны только разработчику для сборки, не пользователю portable-пакета.
