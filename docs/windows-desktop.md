# Дебагыч Desktop 1.3.0 для Windows

## Единый интерфейс с сайтом

В режиме «Сервер Дебагыча» главное окно загружает актуальные HTML, JS, CSS и ресурсы с настроенного HTTPS-сайта через защищённый loopback-прокси. Обновление сайта становится доступно при следующей загрузке страницы. Закройте и снова откройте приложение для гарантированного обновления. Уже открытая страница не заменяется посреди работы.

Питомец остаётся отдельным прозрачным окном того же приложения. Общие аккаунт, backend, проект, переходы к Bug Proof и Fix & Verify сохранены. Изменения native-оболочки, спрайтов и питомца требуют нового установщика. В локальном режиме используется комплектный frontend, этот режим не получает web-обновления автоматически.

Если сайт недоступен, Desktop показывает ошибку соединения. Устаревшая встроенная версия не подставляется автоматически. Первое переключение с 1.2.x требует установки 1.3.0. Результаты и ограничения проверки: [desktop-thin-client.md](desktop-thin-client.md).

## Вход по аккаунту сайта

Версия 1.3.0 использует тот же логин и пароль, что https://debugych.89-22-232-119.nip.io:9443/auth/login. Для обычного подключения серверный ключ не нужен.

1. Закройте предыдущий Дебагыч через «Выход» и установите новую версию.
2. Откройте «Подключение / аккаунт», выберите «Сервер Дебагыча».
3. Оставьте настроенный HTTPS-адрес, введите логин и пароль, нажмите «Войти / подключиться».
4. Главное окно и питомец используют один аккаунт и выбранный проект. Жюри и viewer видят только сохранённый демо-проект; команда получает рабочую область по своим серверным правам.

В Windows Credential Manager сохраняется только непрозрачный серверный сеанс, пароль не записывается в connection.json, frontend или логи. После перезапуска пароль вводить не нужно, пока сеанс действителен. После истечения или отзыва сеанса приложение просит повторный вход. «Выйти из аккаунта» очищает сеанс, старый ключ для этого адреса, выбранный проект и данные окна.

Если раньше подключались по ключу, введите аккаунт в новой форме. После успешного переключения старый ключ больше не используется. Резервный способ входа для оператора находится в дополнительных настройках. Локальный режим сохранён. В режиме сервера WSL и Docker на Windows не требуются.

Не передавайте участникам общий административный пароль: участники команды регистрируются по личным приглашениям. Актуальные пароли не включены в установщик или этот документ. Если сервер требует первоначальную смену временного пароля, выполните её в браузере.

## Установка 1.2

Запустите установочный EXE из `apps/desktop/target/release/bundle/nsis`. Установка выполняется для текущего пользователя, без запроса прав администратора. Выберите каталог, ярлык в меню «Пуск» и создание ярлыка на рабочем столе на завершающем экране. Запускайте установленный «Дебагыч», а не старый portable EXE. Старая portable-версия и её ярлыки не удаляются.

Сборка не подписана сертификатом издателя. Не отключайте SmartScreen и другие средства защиты. Если Windows блокирует запуск, используйте принятую в вашей организации процедуру проверки издателя.

Установщик включает основной EXE, Node runtime, frontend, спрайты и backend bootstrap. Node, Python, и npm не требуются для запуска Windows-клиента. WebView2 обязателен; штатный установщик Tauri проверяет его наличие и при необходимости использует Microsoft bootstrapper. Локальное выполнение тестов отдельно требует совместимого Linux Docker и gVisor. Программа не устанавливает WSL/Docker автоматически.

Переключатель «Показывать питомца на рабочем столе» управляет вторым окном того же приложения. Сворачивание основного окна сохраняет питомца. Закрытие питомца скрывает его. Закрытие основного окна или «Выход» в системном трее завершает приложение и его собственные дочерние процессы. Общие контейнеры и WSL-сервисы остаются работать.

## Подключение и диагностика

«Подключение» сохраняет общий для обоих окон режим и origin API. Local использует loopback HTTP и при необходимости существующий bootstrap. Remote требует HTTPS, не запускает WSL, Docker или локальный backend. До появления сервера недоступный адрес честно показывает ошибку соединения.

«Проверка окружения» доступна сверху и из трея: API, runner/gVisor, Playwright, конфигурация live AI и Docker/runsc. Настройка ключа не считается проверкой внешнего AI API или баланса. Запросы генерации при диагностике не выполняются. Подробности старта сохраняются в каталоге настроек, показанном в окне подключения.

## Обновление и удаление

Закройте Дебагыч через «Выход», затем запустите новый установщик. При обнаружении установленной версии используйте штатное обновление. Установщик не завершает работающий EXE принудительно: сначала попросит закрыть его. Настройки и выбранный проект сохраняются в `%APPDATA%/local.debugych.desktop`; данные backend находятся в существующих серверных volumes.

Для удаления используйте «Установленные приложения» Windows или `uninstall.exe` из каталога установки. Пользовательский профиль и данные backend не удаляются автоматически. Старые portable-копии удаляйте только отдельно по своему решению. Не выбирайте очистку app data, если хотите сохранить WebView-настройки клиента.

Portable-архив `outputs/debugych_desktop_1.2_windows.zip` остаётся дополнительным вариантом. Не запускайте portable и установленную версию одновременно. При обнаружении старой 1.0/1.1 программа покажет PID и полный путь, предложит закрыть старую копию и повторить подключение. Процессы по имени не завершаются.

Сборка из исходников: `npm ci` в apps/web, apps/pet и apps/desktop, затем `scripts/build-windows-app.ps1`. Требуются Rust/MSVC Windows SDK, Node и Python. Установщик использует штатный NSIS pipeline Tauri 2 с минимальным изменением проверки работающего приложения, см. `apps/desktop/installer/README.md`.

Ниже описаны portable-запуск и сохранённая архитектура bootstrap.

Единое приложение Tauri 2 / Windows WebView2: рабочая область AI QA и дополнительное прозрачное окно Desktop Pet v3.2.1. Оба окна принадлежат одному Debugych.exe и используют общий backend, настройки подключения и выбранный проект. Используется существующий production frontend, FastAPI, БД, AI Engine и обязательный gVisor.

## Запуск

1. Распакуйте `debugych_desktop_1.2_windows.zip` в постоянную папку, например `Документы/Debugych`.
2. Запустите **Debugych.exe**. Папка `resources` должна оставаться рядом.
3. Приложение покажет подключение к backend и откроет рабочую область в собственном окне. Терминалы открывать не требуется.
4. Включите «Показывать питомца на рабочем столе» в верхней панели. Положение, размер, высота панели, уменьшение движения, Live/Demo и настройки чата сохраняются.
5. При желании выполните `Create-DesktopShortcut.ps1` для создания ярлыка на эту распакованную копию. После перемещения папки создайте ярлык заново.

## Два окна, одно приложение

Питомец работает при свёрнутом основном окне. Кнопка «Открыть Дебагыч» в настройках питомца восстанавливает основное окно. Ссылки на доказательство, diff и проверку открывают точные сохранённые результаты внутри основного окна. Закрытие питомца или Alt+F4 на нём скрывает только его; включить обратно можно верхним переключателем или меню. Закрытие основного окна и меню «Выход» завершают приложение целиком. Повторный запуск EXE восстанавливает уже работающую копию.

В Live Mode статусы берутся из реальных результатов API. Demo явно отделён от Live. AI-чат сохранён, требует существующего отдельного согласия и доступного backend-провайдера; запуск и показ сохранённых результатов не выполняют платных запросов. В этой версии проверен локальный структурированный ответ чата, реальная LLM повторно не вызывалась.

Настройки подключения меняются в главном окне. Адреса в панели питомца доступны только для чтения. Смена backend сбрасывает выбранный проект и отменяет старые запросы. Выбор проекта в любом окне синхронизируется со вторым. История чата ограничена контекстом проекта и запуска.

Node установленной системы и npm для запуска не нужны: runtime включён в комплект со своей лицензией. Требуется Windows WebView2 Runtime. Дополнительно к установщику доступен portable ZIP. Оба варианта не подписаны сертификатом издателя.

## Автоматический backend

Приложение сначала проверяет настоящий `/api/health` и готовность gVisor. Здоровый backend переиспользуется, без перезапуска контейнеров. Для WSL Ubuntu приложение удерживает собственную скрытую сессию.

Если API недоступен, встроенный bootstrap:

- Проверяет Linux Docker и зарегистрированный runsc.
- Ищет существующий Compose backend, которому принадлежит loopback-порт 8000, включая остановленные контейнеры.
- Запускает только сервисы этого проекта в порядке postgres/redis, runner/supervisor, api, worker. Существующие volumes и серверная конфигурация не заменяются.
- Если готового стека нет, использует backend из комплекта и существующий docker-compose.yml. Создаётся отдельная серверная `.env` без LLM-ключа в каталоге данных приложения. Выполняется обычный `compose up -d --no-recreate --build`.

Первый запуск нового стека может занять несколько минут и требует скачивания обычных Docker/npm/pip зависимостей. Платный AI-запрос при запуске не выполняется.

Для локального QA на компьютере заранее должны быть настроены **WSL2 Ubuntu + Linux Docker + gVisor/runsc**, либо доступен Linux Docker через установленный Docker CLI. Приложение автоматически запускает готовые компоненты, но не устанавливает WSL и gVisor с повышенными правами, не перезапускает Docker ради установки и не отключает изоляцию. При отсутствии зависимостей будет экран ошибки с настройками и повтором, а не ложный успешный запуск. Без ключа доступны импорт, сохранённые результаты, demo и существующие тесты; AI недоступен явно.

## Настройки и будущий сервер

В меню окна **Подключение** можно выбрать:

- Локальный backend: по умолчанию `http://127.0.0.1:8000`.
- Backend на сервере: HTTPS origin без API-ключа, пути и пароля в URL.

После сохранения приложение переподключается. Ключ AI-провайдера остаётся на backend. Для серверного режима локальные контейнеры не запускаются. Сетевой запрос идёт через небольшой встроенный proxy с обычной проверкой TLS; сертификаты не отключаются.

Будущий перенос на сервер отдельно требует развёртывания и пользовательской авторизации. Эта локальная конфигурация не объявляется публичным SaaS. Настройка HTTPS-клиента подготовлена, но реальный удалённый production backend пока не развёрнут и не проверен.

## Данные и завершение

Настройки соединения находятся в `%APPDATA%/local.debugych.desktop/connection.json`. Локальные диагностические журналы и пример backend.env находятся в каталоге данных этого приложения. Ключи и содержимое `.env` не записываются в frontend bundle или release ZIP.

Закрытие приложения завершает только его собственные дочерние процессы frontend, bootstrap и WSL keepalive через Windows Job Objects. Общие контейнеры, Docker и WSL не останавливаются. Backend, который запускается как общий Compose-стек, также сохраняется. Встроенный питомец не имеет отдельного EXE или собственного backend.

Данные питомца хранятся в подкаталоге `pet`. При первом запуске копируются существующие ограниченные по размеру настройки v3.2.1 из `%APPDATA%/local.debugych.desktoppet.v2`, если новых ещё нет. Старая папка не меняется. Для поддержки рядом с EXE создаётся `native-runtime.json` с PID и каталогом настроек, при native panic - ограниченный `native-startup-error.txt`. Эти диагностические файлы не включаются в выпуск.

Внутренний loopback-порт выбирается один раз и сохраняется в `frontend-port.txt`. Благодаря стабильному origin сохраняются настройки веб-интерфейса и выбранный проект между перезапусками. Если порт занят посторонним процессом, приложение сообщает об этом, а не завершает чужой процесс.

## Реализация

- Native host: `apps/desktop`, один идентификатор и процесс Debugych.exe, окна `main` и `pet`.
- Исходники питомца: `apps/pet`, сохранённые спрайты и TypeScript-модули v3.2.1. `scripts/prepare-desktop.py` встраивает их в локальный native frontend и проверяет SHA-256 PNG.
- Встроенный frontend: существующий `apps/web/dist`, без переписывания страниц.
- Backend bootstrap: `scripts/ensure-backend.ps1`, встроен в native host; фиксированный код и отдельные параметры окружения, без изменения Windows ExecutionPolicy.
- HTTP proxy: существующий `scripts/serve-web.mjs`, loopback и собственный свободный порт. HTTPS upstream допускается только при явном выборе серверного режима.
- Packaging: `scripts/package-windows-app.py`. В архиве нет `.env`, БД, user settings или истории Desktop Pet.

Проверки и ограничения версии 1.2 записаны в `docs/desktop-1.2-validation.md`. Полный холодный запуск с нуля нельзя считать подтверждённым по подключению к уже работающему API. Порядок запуска существующих сервисов дополнительно проверяется fixture-тестом без воздействия на общий стек.

Сборка из исходников на Windows с Rust MSVC, C++ Build Tools, Node и Python: `scripts/build-windows-app.ps1`. Python и Rust нужны только разработчику для сборки, не пользователю portable-пакета.
