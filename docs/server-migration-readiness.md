# Подготовка Desktop 1.2 к Linux-серверу

Сервер не развёрнут. Remote Mode подготовлен на стороне клиента, производственная авторизация ещё не реализована.

## Состав сервера

На Linux переносятся FastAPI, PostgreSQL, Redis, Celery worker, supervisor и runner из существующего Compose. Там же остаются Docker, runsc/gVisor, образы pytest/Playwright, хранилище загруженных проектов, отчётов и артефактов. Windows-клиенту нужны только WebView2 и включённый Node runtime для loopback proxy. В Remote Mode клиент не запускает WSL, Docker или локальный backend.

Хост должен поддерживать gVisor и используемые ограничения контейнеров. Runner остаётся без сети, без секретов провайдера и без выполнения кода на Windows. Docker socket не публикуется в интернет. Нужны квоты CPU/RAM/PID/диска, контроль архивов и путей, очистка sandbox и разграничение файлов проектов.

## API и подключение

Существующие `/api/projects`, генерация и результаты запусков, Bug Proof, diff, Fix & Verify, отчёты и companion API используют общий origin. Главные экраны получают API через same-origin proxy; питомец обращается через доверенный Rust adapter. Единственный источник endpoint и проекта - native Runtime/connection.json. Переключение endpoint сбрасывает выбранный проект и старые запросы, revision/session защищают bridge от устаревших сообщений.

Remote принимает только HTTPS origin без credentials, query, fragment и пути. Системная проверка TLS остаётся включённой. До развёртывания нужны DNS, действующий сертификат, reverse proxy, лимиты загрузки, таймауты длительных задач и политика CORS для реально используемых origin. Нельзя просто открыть порт 8000 наружу.

## Авторизация: обязательная следующая доработка

Сегодня API не обеспечивает многопользовательскую изоляцию. Публикация текущего backend в интернет недопустима. Требуются идентификация пользователя, server-side ACL на каждый проект/артефакт/запуск, CSRF/session policy и аудит применения патчей. Подтверждение патча и согласие на передачу исходников LLM сохраняются.

Точку добавления авторизации следует разместить в доверенном native backend adapter (`apps/desktop/src/backend.rs`) и Node proxy (`scripts/serve-web.mjs`). Эти два транспортных компонента обслуживают уже существующие UI-контракты; отдельный клиент для питомца не нужен. Обновляемые пользовательские токены следует хранить в Windows Credential Manager и передавать через ограниченный канал proxy, не через URL, localStorage или JSON настроек. Конфигурация endpoint уже отделена от серверных секретов. Механизм хранения/обновления токенов в 1.2 не реализован.

## Конфигурация

Сервер использует существующие DATABASE_URL, REDIS_URL, SANDBOX_ENABLED, параметры runner/supervisor и образы из `.env.example`/Compose. `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, бюджет и лимиты остаются исключительно в доверенном backend. Desktop сохраняет mode, api_url, backend_root, project_id и pet_visible. В релизные архивы не входят `.env`, backend.env, connection.json, история чата и пользовательские ключи.

Диагностика проверяет `/api/health` и конфигурацию live AI. Она не проверяет баланс, действительность ключа или доступность completion API, поскольку платный запрос запрещён. Это явно показано пользователю.

## Что требует доработки перед миграцией

- Многопользовательская авторизация и ACL, управление сессиями и токенами.
- Серверное хранилище с резервным копированием, retention и квотами.
- HTTPS ingress и ограничения доступа к внутренним сервисам.
- Наблюдаемость без исходников, секретов и содержимого чатов в журналах.
- Проверка remote end-to-end на реальном сервере и тест обновления токена.
- Доверенная подпись Windows-релиза и безопасный канал обновлений.

Автоматическое обновление, серверный деплой и enterprise IAM в Desktop 1.2 не добавлены.
