# Поиск контекста проекта: pgvector и локальные эмбеддинги

Ветка feat/project-rag-ts-coverage, 30 октября 2026. Поиск работает в доверенном backend, отдельно от gVisor. Платный embedding API и ключ LLM для него не нужны.

## Источник требования

В исходном пользовательском ТЗ, раздел 6, pgvector указан условно: семантический поиск при архитектурной необходимости и текстовый fallback при недоступности эмбеддингов. Отдельный официальный документ организаторов не предоставлен. Поэтому реализация закрывает этот пункт пользовательского ТЗ, но не подменяет официальную приёмку жюри.

## Реализация

- PostgreSQL 16 Alpine сохраняет исходную базовую платформу. В собственный образ добавлено расширение pgvector 0.8.7, собранное из исходника с проверкой SHA256. Миграция 004 создаёт extension и таблицу context_chunks. Major PostgreSQL, locale family и data volume не меняются.
- Локальная модель: quantized ONNX paraphrase-multilingual-MiniLM-L12-v2, 384 измерения. Файлы tokenizer/model скачиваются только при доверенной сборке с закреплённой ревизией и SHA256. При запуске приложения загрузок из сети нет. Модель не исполняет код проекта, не читает секреты backend и не обращается к API модели.
- Сначала применяются существующие исключения файлов и редактирование секретов. Затем текст разбивается на фрагменты до 900 символов с именем файла и диапазоном исходных строк. Векторы нормализуются; pooling использует attention mask. Максимальная длина embedding-input 256 токенов, CPU inference в batches по 2, один вычислительный поток.
- Индекс ограничен 160 фрагментами и 2 млн символов входа; превышение отклоняется до embedding inference. Это ограниченный MVP, не индексатор произвольного monorepo. При недостаточном контексте автоматический workflow останавливается на manual_review_required.
- Поиск PostgreSQL использует настоящий cosine operator `<=>` с обязательными условиями project_id, version и encoder. Для небольшого ограниченного индекса выбран точный поиск, без ANN и риска отфильтрованных соседей другого проекта. Обычный индекс project_id ограничивает область поиска.
- Версия зависит от очищенных файлов, границ фрагментов и идентификатора encoder. Неизменённый индекс повторно используется; изменения заменяют его целиком под блокировкой проекта. Старые версии не участвуют в выдаче. Удаление проекта удаляет производный индекс.
- SQLite поддерживает тот же жизненный цикл для локальной разработки: локальное cosine-сравнение при доступной модели или явный lexical-fallback. При отсутствии/ошибке embedding-модели нет попытки заменить её платным API.

Векторы и очищенные фрагменты остаются приватными данными проекта. Они не публикуются в публичном демо и не передаются соседним аккаунтам. Администратор сохраняет существующие административные права. Содержимое запросов и фрагментов в серверные логи не пишется; hide_parameters скрывает значения SQL-параметров и при ошибках БД.

## Связь с генератором

Генератор сначала извлекает требования из полных документов и проверяет точные цитаты. После этого локальный retrieval подбирает исходники по требованиям. Для маленького проекта передаётся весь код, помещающийся в выделенные 12 000 символов source context. Для большего выбирается представительный фрагмент на каждое требование, с полями partial и исходными диапазонами строк. Если набор не помещается или соответствие не найдено, нужен manual review. Требования не вырезаются ради успешного прогона.

Метаданные context_retrieval в запуске содержат метод, версию, число фрагментов, режим full-source/retrieved-fragments и ссылки на исходные строки. Это свидетельство подбора, а не доказательство успешной отправки LLM или корректности тестов. В Test Studio они раскрываются отдельно. Существующие согласие, строгая валидация, технический runner и лимиты LLM остаются обязательными.

RAG здесь подключён к первичной генерации. Repair/patch stages сохраняют прежние лимиты полного контекста и могут остановиться на слишком большом проекте. Не заявляется поддержка произвольного размера или гарантия полноты поиска.

## Поиск без AI-генерации

В Test Studio раскройте «Поиск по коду и требованиям». Endpoint:

```text
POST /api/projects/{project_id}/context-search
{"query":"оплата при точном балансе","limit":6}
```

Запрос ограничен 1000 символами, выдача до 10 фрагментов. Он доступен только в собственной рабочей области; для публичного демо скрыт и не проксируется. Первый запрос обновляет индекс, следующие используют его версию. Допускаются одновременно два поисковых запроса API; занятость возвращает 429. Размер производного индекса включён в оценку хранилища.

Этот бесплатный синхронный endpoint обрабатывает код и Markdown, не запускает парсеры PDF/DOCX. Бинарные документы по-прежнему извлекаются в основном существующем AI workflow после согласия. Сфера поиска явно подписана в UI и response.document_scope. API-ключ не требуется, попытка AI не списывается.

## Ресурсы и fallback

В production только доверенные API и worker получили лимит памяти 768 MiB вместо 512 MiB под локальную модель. На проверенном VPS 4 GiB RAM. Лимиты CPU/RAM/времени gVisor, сетевой запрет, runtime и пользовательские квоты не увеличены. Модель GPT-6 Luna и финансовые резервы прежние.

Для отключения embedding inference используйте RAG_EMBEDDINGS=lexical. При запуске вне контейнера без RAG_MODEL_DIR также включается текстовый поиск. Это не семантический режим, UI и API показывают lexical-fallback. Лексические hash-векторы служат только совместимому хранению; fallback ранжирует реальные совпадения токенов и не выдаёт hash collisions за семантическую близость.

Cold build скачивает около 135 MB весов и токенизатора. Для семантического режима нужен доступ хоста сборки к публичному репозиторию модели; после сборки inference локальный. Если веса недоступны или не прошли проверку, Docker-сборка продолжает работу с явным текстовым fallback, не загружая недостоверную модель. Для обязательной проверенной загрузки используйте prepare-embeddings.py без --optional. Повторить загрузку после восстановления доступа можно пересборкой Docker embeddings stage без его cache. Подготовить проверенные файлы отдельно можно scripts/prepare-embeddings.py --output DIRECTORY. Пакеты ONNX/tokenizers из requirements-embeddings.txt устанавливаются только в доверенный API/worker image, не в тестовые sandbox.
