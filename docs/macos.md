# Запуск Дебагыча на macOS

Ветка `release/macos-web-support`. Это web-приложение с macOS-launcher, а не перенос Windows Desktop Pet и не подписанный .app/.dmg.

## Схема работы

На Mac работают браузер и небольшой Node-сервер, который раздаёт готовый frontend и проксирует запросы на loopback backend. AI, база, тесты и gVisor остаются в существующем Linux backend. Источники проекта загружаются в него через тот же API, не исполняются напрямую на Mac. API-ключи остаются в серверной .env. Tauri и отдельный AI-клиент не добавляются.

Mac с Intel или Apple Silicon использует один и тот же JavaScript и готовый dist. Установите Node.js 22+ для своей архитектуры с [официального сайта](https://nodejs.org/en/download). Rosetta для launcher не требуется; реальный запуск на обеих архитектурах пока не проверен.

gVisor требует Linux 5.6+ и поддерживает x86_64 / ARM64: [официальная установка](https://gvisor.dev/docs/user_guide/install/). Поэтому полноценный backend нельзя запускать непосредственно в ядре macOS. Linux VM на Mac либо уже существующий Linux-компьютер с backend сохраняют обязательную изоляцию. Наличие обычного Docker Desktop не означает, что runsc уже установлен.

## Вариант 1: backend уже доступен на Mac через localhost

1. Распакуйте `debugych-web-macos.zip` в обычную пользовательскую папку.
2. Backend с рабочим gVisor должен отвечать на `http://127.0.0.1:8000/api/health`.
3. Дважды нажмите `Start Debugych.command`. Откроется Terminal и браузер `http://127.0.0.1:8798/`.
4. Оставьте Terminal открытым. Ctrl+C завершает только этот frontend, не общие контейнеры и не backend.

Эквивалент из Terminal:

```bash
cd "/путь/к/debugych-web-release"
bash scripts/start-local.sh --reuse-backend --open
```

Архив содержит готовый dist, поэтому npm install для обычного запуска не нужен. В ZIP выставлены Unix-права 755 для .command/.sh и окончания строк LF. Если ваша программа распаковки потеряла права, используйте `bash "Start Debugych.command"` из этой папки. Не отключайте Gatekeeper и не обходите предупреждения macOS. Если политика компьютера блокирует запуск, используйте разрешённую администратором процедуру.

## Вариант 2: существующий Linux backend через SSH

На Linux должны работать обычный стек Дебагыча, gVisor и SSH. Его API остаётся привязанным к loopback, наружу 8000 открывать не требуется.

В отдельном Terminal на Mac:

```bash
# Замените user@linux-host своим настоящим SSH-адресом.
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18000:127.0.0.1:8000 user@linux-host
```

Оставьте туннель открытым. В папке приложения:

```bash
bash scripts/start-local.sh --reuse-backend --api-url http://127.0.0.1:18000 --open
```

Это тот же backend, тот же pipeline и те же результаты. Launcher не хранит SSH-пароли, не управляет ключами и не подтверждает неизвестный SSH fingerprint. Подключение SSH настраивается пользователем обычным способом. Туннель можно использовать и для Linux VM на самом Mac.

## Вариант 3: Linux VM с уже настроенным Docker / runsc

Используйте существующую Ubuntu/Debian VM подходящей архитектуры, Linux Docker и обычный `infra/install-gvisor.sh` внутри VM. Установщик требует sudo, apt/systemd и перезапускает Docker; launcher сам его не запускает. Не запускайте этот установщик на macOS.

Проще всего распаковать тот же release внутри VM, настроить серверную .env без раскрытия ключа, выполнить существующий `docker compose up -d --build` и подключить Mac по варианту 2. Данные остаются в прежних Compose volumes.

Если Docker CLI на Mac уже подключён к совместимому Linux engine с runsc, можно использовать:

```bash
bash scripts/start-local.sh --start-backend --open
```

Перед запуском проверяется Linux engine и наличие runsc. Используется существующий docker-compose.yml. Для удалённого Docker context опубликованный порт находится на удалённом engine, а не автоматически на Mac: настройте SSH-туннель и укажите `--api-url` как выше. При недоступности API launcher завершится с ошибкой, а не объявит приложение работающим.

Если .env отсутствует, создаётся локальный пример без ключа. Для удалённой установки предпочтительнее хранить .env на Linux и запускать Compose там. Не передавайте .env в frontend.

## Диагностика и настройки

```bash
bash scripts/start-local.sh --doctor
# Для туннеля:
bash scripts/start-local.sh --doctor --api-url http://127.0.0.1:18000
# Другой свободный web-порт:
bash scripts/start-local.sh --reuse-backend --port 8799 --open
# Сборка изменённых исходников (требуется npm и доступ к npm registry):
bash scripts/start-local.sh --reuse-backend --build
```

`--doctor` не запускает AI или Compose, не меняет файлы, не показывает ключи. Успешное подключение backend даёт exit code 0, недоступность или неработающий gVisor дают 2. Docker может отсутствовать на Mac при использовании готового backend через туннель.

Без LLM-ключа backend допустим, если gVisor доступен: launcher явно сообщает об отсутствии AI; сохранённые результаты и существующие тесты остаются доступны. Демо-only runner не считается полноценным backend. Недоступный сервер, занятый web-порт, неправильный URL или отсутствие Node дают понятную ошибку. Запуск приложения не создаёт AI-задачу и не расходует платные запросы.

По умолчанию API разрешён только через HTTP loopback. Внешний backend подключайте через защищённый туннель, а не открытием локального API без авторизации в интернет.

## Проверка реализации и оставшиеся ограничения

- Bash wrappers проверены `bash -n`, пути с пробелами поддержаны.
- Node launcher протестирован на Windows Node 24 и Linux Node 22. Тесты охватывают URL / параметры, отказ demo-only backend, работу без AI-ключа, proxy и остановку собственного сервера.
- Интеграционный launcher-тест использует явно тестовый локальный health/API fixture, без LLM. Он не доказывает запуск gVisor внутри macOS.
- `--doctor` отдельно проверен на настоящем общем backend с доступным gVisor. Рабочие контейнеры не перезапускались.
- Сборка frontend и server уже проверены в Linux x64; предыдущий web release имеет 20 браузерных проверок и реальный бесплатный Verify сохранённого патча.
- Настоящего Mac здесь нет: Finder/Terminal, Safari, Apple Silicon и Intel Mac пока требуют приёмки на реальном устройстве. Пакет подготовлен для macOS, но не объявляется полностью проверенным на ней.
- Нативный Windows Desktop Pet в этот пакет не портирован. Работает web-версия в браузере Mac с тем же backend.

Проверка на Mac перед приёмкой: `--doctor`, открытие главной страницы, импорт исходников, Test Studio/Bug Lab на сохранённом проекте, просмотр diff, бесплатный Verify существующего патча, перезагрузка, Ctrl+C и повторный запуск. Для нового платного AI-цикла требуется отдельное согласие. Изоляцию или подтверждение применения патча отключать нельзя.
