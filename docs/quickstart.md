# Подготовка и локальный запуск

## Требования к хосту

Нужны Python 3, Docker Compose 2.24.4+ и Linux Docker Engine с зарегистрированным runsc. На Windows запускайте команды внутри подготовленного WSL2/Linux-окружения. Наличие Docker Desktop само по себе не доказывает поддержку gVisor.

На выделенном Debian/Ubuntu Docker-хосте администратор может выполнить `sudo bash infra/install-gvisor.sh`. Скрипт устанавливает runtime и перезапускает Docker. Сначала проверьте влияние на остальные контейнеры. Локальный launcher сам не устанавливает пакеты, не меняет daemon.json и не вызывает restart Docker.

Для подготовки production-хоста есть отдельный scripts/prepare-server-host.sh; его применение требует проверки инфраструктуры. Не запускайте установку runtime ради проверки UI на общем рабочем сервере.

## Проверка без изменений

```sh
python3 scripts/preflight.py
python3 scripts/preflight.py --json
```

Проверяются доступ к Docker, Linux engine, регистрация runsc, версия Compose, корректность конфигурации и порты 8000/8080. Занятый порт допускается только если он опубликован работающим контейнером того же проекта debugych-local. Чужие контейнеры и процессы не останавливаются. Диагностика не выводит развёрнутую конфигурацию и значения секретов. При проблеме команда возвращает ненулевой exit code.

Это проверка предварительных условий, без запуска пользовательского кода. Ошибка исполнения runtime дополнительно обнаруживается healthcheck supervisor и фактическим gVisor smoke в CI.

## Запуск приложения

```sh
sh scripts/start-compose.sh
```

После успешного preflight выполняется `docker compose --project-name debugych-local -f docker-compose.yml up --build -d --wait`. Откройте http://127.0.0.1:8080/. Для изолированного запуска можно задать DEBUGYCH_LOCAL_PROJECT; имя проверяется, порты остаются теми же. Порты доступны только на loopback. Для удалённого Linux-хоста используйте защищённый SSH-туннель либо отдельную production-инструкцию; не открывайте dev-API на 0.0.0.0.

Сборка Playwright с Chromium может потребовать времени и сетевого доступа к реестрам пакетов. Пользовательский тестовый sandbox сетевого доступа не получает. Если зависимости нельзя загрузить, сборка не объявляется успешной.

## Типичные остановки

| Причина | Действие |
|---|---|
| Docker недоступен | Проверить запуск engine, выбранный context и права пользователя |
| Нет runsc | Явно подготовить подходящий Linux Docker-хост; не включать runc fallback |
| Порт занят другим процессом | Выбрать отдельное окружение; не останавливать чужой процесс автоматически |
| Supervisor не healthy | Проверить его журнал и регистрацию runtime; не снимать зависимость ради зелёного старта |
| Нет LLM-ключа | Приложение запускается; использовать подготовленное демо или сохранённые тесты |
| Бюджет AI исчерпан | Дождаться сброса или отдельно согласовать лимит; не подменять генерацию демо-ответом |

Новый launcher проверен 30 октября на отдельном проекте debugych-readiness-20261030 с отключённым LLM-ключом: сборка и up --wait прошли; загруженные Python-тесты 2/2 и Playwright 1/1 выполнились в runsc с покрытием. Проверка повторного допуска своего проекта прошла; другой проект с занятыми портами получил отказ. На свежесобранном API прошли 202 backend-теста. [Предыдущий полный CI](https://github.com/tribalsm/debugych/actions/runs/40821353420); текущая ветка проходит отдельный CI.

Во время автоматической проверки WSL локальный Docker получил SIGTERM и остановил контейнеры; OOMKilled=false. Два повторных обращения получили connection refused. После запуска с удерживаемым Linux-сеансом smoke снова прошёл. Источник SIGTERM не установлен; длительная работа WSL после закрытия запускающего сеанса не подтверждена. Для постоянного стенда используйте управляемый Linux-хост, а lifecycle локального WSL проверьте на целевой машине.
