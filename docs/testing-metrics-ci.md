# Метрики успешности и экспорт для CI

Обновлено 30 октября 2026 года. Ветка `feat/qa-metrics-ci-export`. Платные LLM-запросы для этих проверок не используются.

## Что показывает отчёт

Вкладка «Отчёт» содержит метрики выбранного проекта за 7 дней, 30 дней или всё время. Это статистика сохранённых результатов, а не оценка LLM и не гарантия корректности программы.

| Метрика | Расчёт |
|---|---|
| Пройдено проверок | passed / (passed + failed + errors); skipped показаны отдельно |
| Успешные запуски | completed с хотя бы одним passed, без failed/errors / все завершённые попытки run, включая технически failed |
| Ошибки тестов | Результаты cases со статусом error, например ошибка fixture |
| Сбои задания | Попытки со статусом failed; это не подтверждённые дефекты приложения |
| Без корректного отчёта | Пустые, повреждённые или противоречивые результаты |

Повторные прогоны учитываются отдельно; одинаковый ID не дублируется. Анализ, родительский autonomous, Bug Proof и verify не входят в знаменатель запусков run. Вложенный реальный запуск autonomous учитывается один раз. Проверка патча по-прежнему отображается в отдельном фактическом отчёте и истории.

Отсутствие данных показывается как «Нет данных», а не 100%. Все skipped не образуют успешный запуск. Неполные сводки старого демо рассчитываются по cases; предоставленная сводка обязана совпадать с ними. Наивные UTC timestamps из SQLite обрабатываются как UTC. В ограниченном периоде отсутствующие, некорректные и будущие даты исключаются явно.

## JUnit XML

После завершения выберите нужный запуск в интерфейсе и нажмите «JUnit XML». Формат подходит для систем CI, умеющих читать JUnit. API:

```text
GET /api/exports?project_id=UUID&format=junit&run_id=UUID
```

Без run_id выбирается последний завершённый run этого проекта. Проверяется принадлежность запуска проекту и право пользователя на проект. Для verify экспортируется только регрессия, без ожидаемо падающего baseline и без повторного focused. Неполученная регрессия или незавершённый запуск дают 409. Старое демо с финальной регрессией в верхнем уровне поддерживается отдельно.

Assertions становятся `<failure>`, ошибки выполнения тестов становятся `<error>`, пропуски становятся `<skipped>`. Сбой runner, пустой отчёт или несовпадающая сводка добавляют технический `<error>` даже при наличии частично успешных тестов. Неизвестные статусы отклоняются. XML экранируется, запрещённые управляющие символы удаляются. Покрытие не подменяется JUnit: оно остаётся в QA JSON и интерфейсе.

## GitHub Actions

1. Подготовьте и проверьте тесты своего проекта в Дебагыче.
2. Во вкладке «Отчёт» скачайте «GitHub Actions .zip» и проверьте содержимое.
3. Распакуйте пакет в корень соответствующего репозитория, сохранив `.github/workflows/debugych-qa.yml` и `debugych_ci/`.
4. Добавьте repository variable `DEBUGYCH_BASE_URL` с HTTPS-origin доверенного сервера, например `https://debugych.46-226-161-120.sslip.io:9443`.
5. Добавьте Actions secrets `DEBUGYCH_USERNAME` и `DEBUGYCH_PASSWORD` выделенного обычного аккаунта. Администратор, owner token и LLM API key не нужны.
6. Запустите workflow «Debugych QA» вручную в Actions. Автоматический запуск для pull_request_target и передача секретов fork PR не включены.

Скачанный stdlib-клиент `debugych_ci/run.py` загружает исходники checkout и точные экспортированные тесты во временный личный проект. SHA256 каждого тестового модуля проверяется перед отправкой. На сервере импортируются только указанные в manifest тесты, а не все обнаруженные тесты репозитория. Затем используется существующий gVisor Runner с прежними лимитами и отсутствием внешней сети. Код проекта не запускается на GitHub runner. Workflow имеет только contents: read и не сохраняет checkout credentials.

После выполнения скачиваются `debugych-report/junit.xml` и `summary.json`, публикуемые как Actions artifact. Exit code 0 требует completed, runtime runsc, хотя бы одного непропущенного теста и отсутствия failures/errors. Assertion, all-skipped, ошибка инфраструктуры или неподтверждённый runtime дают ненулевой exit code. Ошибка настройки/связи также проваливает job. Временный проект удаляется в finally; при потере связи или незавершённом задании выводится его ID для последующей очистки.

Клиент не следует HTTP-redirect, принимает только HTTPS-origin без userinfo и не пишет пароль, cookie, тела ответов или исходники в console. Серверные пользовательские квоты и общий admission limit сохраняются. Исправлена обнаруженная при проверке блокировка повторного CI-запуска после удаления его временного проекта: слот освобождается только после успешного серверного удаления. Отклонённое удаление занятого проекта сохраняет блокировку.

## Передача кода и ограничения

Пакет не содержит исходники проекта или credentials. Сам запуск workflow намеренно передаёт код серверу, указанному в переменной: используйте доверенный сервер и выделенный аккаунт.

Перед передачей можно посмотреть список файлов без входа и сетевых запросов:

```sh
python debugych_ci/run.py --root . --list-files
```

Скрытые файлы и каталоги, `.env`, symlinks, зависимости, build/output и распространённые имена секретов исключаются. Это не DLP: секреты, встроенные в произвольный исходник, невозможно гарантированно распознать по имени. Проверьте список и содержимое перед использованием. Лимит клиента: 60 исходных файлов / 1.5 МБ, до 40 тестовых модулей одного framework, суммарно до 1.9 МБ. Лимиты Runner не увеличены.

Фиксированные зависимости sandbox и существующие ограничения импортов сохраняются. Это запуск экспортированного набора, а не замена всех тестов исходного репозитория, новая AI-валидация ожиданий или mutation testing. Неуспешный тест сам по себе не становится подтверждённым Bug Proof. Публичное демо остаётся только для просмотра; новый экспорт доступен в своей рабочей области после входа или в гостевой истории с собственными данными.

## Воспроизводимые проверки

- Backend: `pytest tests/integration/test_ci_exports.py` проверяет XML, отдельные типы отказов, регрессию, IDOR, выбор импортируемых модулей, manifest hashes и CI exit codes/cleanup без внешних API.
- Frontend: `npm test` из apps/web проверяет знаменатели, повторы, пропуски, ошибки и UTC-периоды.
- Browser: `tests/e2e/metrics-ci.spec.ts` выполняет настоящее подготовленное демо, проверяет 13/14 = 92.9%, 0/1 успешных запусков, оба скачивания и мобильный экран.
- Опциональная реальная проверка `tests/server/ci-export-live.py` требует DEBUGYCH_CI_LIVE_CHECK=1, HTTPS DEBUGYCH_BASE_URL и локальный приватный DEBUGYCH_ACCOUNT_CREDENTIALS. Она скачивает пакет с сервера и запускает именно скачанный клиент на исправном и дефектном Python/Playwright-коде. Тесты между фазами не меняются; только контрольный исходник. Ни модель, ни применение патча не вызываются.
